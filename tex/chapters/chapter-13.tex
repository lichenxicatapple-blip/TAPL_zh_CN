\chapter{引用}
\label{chap:13}

\section*{概述}

到目前为止，我们考察了多种纯语言特性，包括函数抽象、数字和布尔值一类
基本类型，以及记录和变体一类结构类型。这些特性构成了多数程序语言的骨架：
既包括 Haskell 一类纯函数式语言、ML 一类“以函数式为主”的语言，也包括 C
一类命令式语言和 Java 一类面向对象语言。

多数实用程序语言还包含多种非纯特性，无法用此前的简单语义框架描述。特别是，
这些语言中的项求值除了产生结果，还可能给可变变量赋值（引用单元、数组、
可变记录字段等），对文件、显示设备或网络连接执行输入输出，通过异常、跳转
或续延作非局部控制转移，参与进程间同步与通信，等等。程序语言文献把计算的
这类“副作用”更一般地称为\termfirst{计算效应}{computational effect}。

本章将看到，怎样把一种计算效应——可变引用——加入此前的演算。主要扩展是
显式处理\termfirst{存储}{store}（或堆）。这项扩展很容易定义，最有意思的
部分，是必须细化类型保持性定理~\ref{thm:13.5.3} 的陈述。第
\ref{chap:14}~章会考察另一类效应：异常与非局部控制转移。

\translatornote{本译本在 \texttt{code/simple/} 的 Rust 参考实现中，以
显式存储结构实现本章的分配、解引用和赋值规则，并测试别名、共享状态及存储
增长。Rust 的所有权和借用机制没有被用来替代本章的对象语言规则；实现仍然
忠实模拟原书的抽象存储。}

\section{引言}
\label{sec:13.1}

几乎每种程序语言\footnote{即使 Haskell 一类“纯函数式”语言，也可通过
monad 等扩展做到。}都提供某种赋值操作，用来改变先前分配的一块存储的内容。
\footnote{本章研究带 \(\tapltype{Unit}\) 与引用的简单类型 lambda 演算
（图~\ref{fig:13-1}），相应的 OCaml 实现为 \texttt{fullref}。}
在一些语言中，尤其是 ML 及其近亲，名字绑定机制与赋值机制彼此分开。可以有
一个值为数字 \(5\) 的变量 \(x\)，也可以有一个值为引用（或指针）的变量
\(y\)，后者指向当前内容为 \(5\) 的可变单元；程序员能看见二者的区别。
我们可以把 \(x\) 加到另一个数字上，却不能给它赋值。可以直接用 \(y\) 把
新值写入它所指的单元，例如 \(y:=84\)，却不能直接把 \(y\) 作为
\(\mathit{plus}\) 的参数；必须显式解引用，写作 \(!y\)，才能取得当前内容。
而在多数其他语言，尤其是包括 Java 在内的整个 C 家族中，每个变量名都指向
可变单元；为取得当前内容而对变量解引用的操作是隐式的。\footnote{严格地说，
C 或 Java 中多数类型为 \(T\) 的变量，实际应看作指向
\(\operatorname{Option}(T)\) 型值之单元的指针，因为变量内容既可以是正常
值，也可以是特殊值 \texttt{null}。}

为形式研究，把这两种机制分开很有用；本章紧随 ML 的模型。把这里的经验用于
类 C 语言很直接：合并一些区别，并让解引用等特定操作由显式变为隐式。
\footnote{从语言设计角度看，也有充分理由支持这种分离。把可变单元的使用
变成显式选择而不是默认行为，可以鼓励以函数式为主、少量使用引用的编程风格；
这种实践往往使程序明显更易编写、维护和推理，存在并发等特性时尤其如此。}

\subsection*{基本操作}

引用的基本操作是分配、解引用和赋值。要分配引用，使用
\(\mathsf{ref}\) 运算符，并给出新单元的初值：
\[
r=\mathsf{ref}\ 5
\qquad\blacktriangleright\qquad r:\tapltype{Ref}\ \tapltype{Nat}.
\]
类型检查器的响应说明，\(r\) 的值是一个引用，它指向的单元始终存放数字。
用解引用运算符 \(!\) 读取这个单元的当前值：
\[
!r\quad\blacktriangleright\quad5:\tapltype{Nat}.
\]
用赋值运算符改变单元内保存的值：
\[
r:=7\quad\blacktriangleright\quad\mathsf{unit}:\tapltype{Unit}.
\]
赋值结果是平凡值 \(\mathsf{unit}\)，见 \S\ref{sec:11.2}。再次解引用
\(r\)，便看到更新后的值：
\[
!r\quad\blacktriangleright\quad7:\tapltype{Nat}.
\]

\subsection*{副作用与顺序执行}

赋值表达式的结果是平凡值 \(\mathsf{unit}\)，这正好与
\S\ref{sec:11.3} 定义的顺序执行记法配合。为了依次求值两个表达式并返回
第二个表达式的值，可以写：
\[
(r:=\taplsucc{(!r)};\ !r)
\quad\blacktriangleright\quad8:\tapltype{Nat},
\]
而不必写等价却更繁琐的：
\[
(\lambda\_:\tapltype{Unit}.\,!r)\,
(r:=\taplsucc{(!r)})
\quad\blacktriangleright\quad9:\tapltype{Nat}.
\]
把第一个表达式的类型限制为 \(\tapltype{Unit}\)，使类型检查器能捕获一些
愚蠢错误：只有当第一个值保证无关紧要时，才允许丢弃它。

若第二个表达式也是赋值，整个序列的类型仍是 \(\tapltype{Unit}\)，因此
可以合法地把它放在另一个分号左边，构造更长的赋值序列：
\[
(r:=\taplsucc{(!r)};\ r:=\taplsucc{(!r)};\
 r:=\taplsucc{(!r)};\ r:=\taplsucc{(!r)};\ !r)
\quad\blacktriangleright\quad13:\tapltype{Nat}.
\]

\subsection*{引用与别名}

必须牢记：绑定到 \(r\) 的引用，与该引用所指向的存储单元是不同的。

\begin{center}
\begin{tikzpicture}[>=Stealth,baseline]
  \node[draw,rounded corners,minimum width=12mm,minimum height=7mm] (r) {\(r\)};
  \node[draw,minimum width=16mm,minimum height=10mm,right=25mm of r] (c) {\(5\)};
  \draw[->,thick] (r) -- (c);
\end{tikzpicture}
\end{center}

例如把 \(r\) 的值绑定到另一变量 \(s\)，从而复制 \(r\)：
\[
s=r\qquad\blacktriangleright\qquad s:\tapltype{Ref}\ \tapltype{Nat},
\]
得到复制的只是引用，即图中的箭头，而不是单元：

\begin{center}
\begin{tikzpicture}[>=Stealth,baseline]
  \node[draw,rounded corners,minimum width=12mm,minimum height=7mm] (r) {\(r\)};
  \node[draw,rounded corners,minimum width=12mm,minimum height=7mm,below=6mm of r] (s) {\(s\)};
  \node[draw,minimum width=16mm,minimum height=10mm,right=28mm of r,yshift=-5mm] (c) {\(5\)};
  \draw[->,thick] (r) -- (c);
  \draw[->,thick] (s) -- (c);
\end{tikzpicture}
\end{center}

给 \(s\) 写入新值，再通过 \(r\) 读出即可验证：
\[
s:=82\blacktriangleright\mathsf{unit},
\qquad
!r\blacktriangleright82:\tapltype{Nat}.
\]
称引用 \(r\) 与 \(s\) 是同一单元的
\termfirst{别名}{alias}。

\begin{exercise}[\(\star\)]
\label{ex:13.1.1}
画出类似的图，说明求值
\[
a=\{\mathsf{ref}\ 0,\mathsf{ref}\ 0\}
\]
和
\[
b=(\lambda x:\tapltype{Ref}\ \tapltype{Nat}.\{x,x\})
  (\mathsf{ref}\ 0)
\]
各自产生的效果。
\end{exercise}

\subsection*{共享状态}

存在别名会使含引用的程序很难推理。例如表达式
\((r:=1;\ r:=!s)\) 先把 \(1\) 赋给 \(r\)，紧接着又用 \(s\) 的当前值
覆盖它。除非把它放在 \(r\) 与 \(s\) 是同一单元之别名的上下文中，否则它
与单次赋值 \(r:=!s\) 效果完全相同。

当然，别名也是引用十分有用的一项重要原因。特别是，它让程序的不同部分之间
可以建立“隐式通信通道”——\termfirst{共享状态}{shared state}。例如，
定义一个引用单元和两个操纵其内容的函数：
\[
\begin{aligned}
c&=\mathsf{ref}\ 0:\tapltype{Ref}\ \tapltype{Nat},\\
\mathit{incc}&=\lambda x:\tapltype{Unit}.\
 (c:=\taplsucc{(!c)};\ !c):
 \tapltype{Unit}\to\tapltype{Nat},\\
\mathit{decc}&=\lambda x:\tapltype{Unit}.\
 (c:=\taplpred{(!c)};\ !c):
 \tapltype{Unit}\to\tapltype{Nat}.
\end{aligned}
\]
调用 \(\mathit{incc}\ \mathsf{unit}\) 得到 \(1\)，它对 \(c\) 的修改可以
由随后调用 \(\mathit{decc}\ \mathsf{unit}\) 观察到，后者得到 \(0\)。

若把 \(\mathit{incc}\) 与 \(\mathit{decc}\) 打包进记录：
\[
o=\{i=\mathit{incc},d=\mathit{decc}\}
:\{i:\tapltype{Unit}\to\tapltype{Nat},
   d:\tapltype{Unit}\to\tapltype{Nat}\},
\]
就能把整个结构作为单元传递，并用其分量对 \(c\) 中的共享状态作递增、递减
操作。实际上，我们已经构造了一种简单对象。\chapref{18}会详细发展
这个思路。

\subsection*{复合类型的引用}

引用单元不必只存放数字：上述基本操作允许创建指向任意类型之值的引用，包括
函数。例如，可以用函数引用低效地实现数字数组。令
\[
\texttt{NatArray}=\tapltype{Ref}\,
(\tapltype{Nat}\to\tapltype{Nat}).
\]
新数组分配一个引用单元，填入一个接受任意索引都返回 \(0\) 的函数：
\[
\mathit{newarray}=
\lambda\_:\tapltype{Unit}.\
\mathsf{ref}\,(\lambda n:\tapltype{Nat}.\,0)
:\tapltype{Unit}\to\texttt{NatArray}.
\]
查找数组元素时，把保存的函数应用于所需索引：
\[
\mathit{lookup}=
\lambda a:\texttt{NatArray}.\lambda n:\tapltype{Nat}.\
(!a)\,n
:\texttt{NatArray}\to\tapltype{Nat}\to\tapltype{Nat}.
\]

编码中有意思的是更新函数。它接受数组、索引和要保存在该索引的新值；先创建
一个新函数，再把它存入引用。新函数在被问及这个索引的值时，返回传给更新
操作的新值；对所有其他索引，则把查找交给引用先前保存的函数。
\[
\begin{aligned}
\mathit{update}={}&
\lambda a:\texttt{NatArray}.\lambda m:\tapltype{Nat}.
\lambda v:\tapltype{Nat}.\\
&\mathsf{let}\ \mathit{oldf}=!a\ \mathsf{in}\\
&a:=(\lambda n:\tapltype{Nat}.\
\mathsf{if}\ \mathit{equal}\ m\ n\
\mathsf{then}\ v\ \mathsf{else}\ \mathit{oldf}\ n)
\\[-2pt]
&:\texttt{NatArray}\to\tapltype{Nat}\to
\tapltype{Nat}\to\tapltype{Unit}.
\end{aligned}
\]

\begin{exercise}[\(\star\star\)]
\label{ex:13.1.2}
若把更新更紧凑地定义成：
\[
\begin{aligned}
\mathit{update}={}&
\lambda a:\texttt{NatArray}.\lambda m:\tapltype{Nat}.
\lambda v:\tapltype{Nat}.\\
&a:=(\lambda n:\tapltype{Nat}.\
\mathsf{if}\ \mathit{equal}\ m\ n\
\mathsf{then}\ v\ \mathsf{else}\ (!a)\,n),
\end{aligned}
\]
其行为相同吗？
\end{exercise}

指向含有其他引用之值的引用也很有用，可以用来定义可变列表、可变树等数据
结构。这类结构通常还涉及\chapref{20}将引入的递归类型。

\subsection*{垃圾回收}

正式处理引用之前，最后要提到存储释放。我们没有提供基本操作，在不再需要
引用单元时显式释放它们；与许多现代语言（包括 ML 与 Java）一样，依赖运行时
系统执行\termfirst{垃圾回收}{garbage collection}，收集并重用程序已无法
到达的单元。这不只是语言设计的偏好问题：存在显式释放操作时，要实现类型
安全极其困难。原因是熟悉的悬垂引用问题：先分配一个保存数字的单元，把它的
引用存入某数据结构并使用一段时间，然后释放它，再分配一个保存布尔值的新
单元；新单元可能重用同一块存储。现在，同一存储单元可能有两个名字，一个
类型是 \(\tapltype{Ref}\ \tapltype{Nat}\)，另一个类型是
\(\tapltype{Ref}\ \tapltype{Bool}\)。

\begin{exercise}[\(\star\star\)]
\label{ex:13.1.3}
说明上述情形怎样导致类型安全性遭到破坏。
\end{exercise}

\section{类型}
\label{sec:13.2}

\(\mathsf{ref}\)、\(:=\) 与 \(!\) 的类型规则直接来自我们为它们规定的
行为：
\[
\inferrule*[right=\textsc{T-Ref}]
 {\Gamma\mid\Sigma\vdash t_1:T_1}
 {\Gamma\mid\Sigma\vdash\mathsf{ref}\ t_1:
  \tapltype{Ref}\ T_1}
\]
\[
\inferrule*[right=\textsc{T-Deref}]
 {\Gamma\mid\Sigma\vdash t_1:\tapltype{Ref}\ T_{11}}
 {\Gamma\mid\Sigma\vdash!t_1:T_{11}}
\qquad
\inferrule*[right=\textsc{T-Assign}]
 {\Gamma\mid\Sigma\vdash t_1:\tapltype{Ref}\ T_{11}\\
  \Gamma\mid\Sigma\vdash t_2:T_{11}}
 {\Gamma\mid\Sigma\vdash t_1:=t_2:\tapltype{Unit}}.
\]
其中存储类型 \(\Sigma\) 的含义将在 \S\ref{sec:13.4} 说明。

\section{求值}
\label{sec:13.3}

形式化引用的操作行为时会出现更微妙的问题。只要问一句“类型
\(\tapltype{Ref}\ T\) 的值应是什么”，就能看出原因。必须考虑的关键观察
是：求值 \(\mathsf{ref}\) 运算符应当真正做一件事——分配一些存储——并
产生指向这块存储的引用。

那么，引用究竟是什么？

多数程序语言实现中的运行时存储，本质上就是巨大的字节数组。运行时系统追踪
数组中哪些部分正在使用；需要分配新引用单元时，从空闲区域分出足够大的片段
（整数单元可能为 4 字节，浮点单元可能为 8 字节，等等），标记为在用，再
返回新分配区域开头的索引，通常是 32 位或 64 位整数。这些索引就是引用。

目前没有必要具体到这种程度。可以把存储看作值的数组，而不是字节的数组，
从而抽象掉不同值的运行时表示大小不同这一事实。还可以进一步抽象掉引用
（即数组索引）是数字这一事实。把引用取作某个没有解释的
\termfirst{存储位置}{store location}集合 \(\mathcal L\) 的元素；存储则
只是从位置 \(l\) 到值的部分函数。用元变量 \(\mu\) 表示存储。于是，引用
就是一个位置，即存储的抽象索引。从现在开始使用“位置”而不用“引用”或
“指针”，以强调这种抽象性质。\footnote{这样抽象地处理位置，使我们无法
模拟 C 等底层语言中的指针算术；这是有意的限制。指针算术偶尔很有用，尤其
适合实现垃圾回收器等运行时系统底层组件，却无法由多数类型系统追踪：知道
存储位置 \(n\) 含有 \(\tapltype{Float}\)，并不能让我们推断位置 \(n+4\)
的类型。在 C 中，指针算术是造成类型安全破坏的著名根源。}

接着，要扩展操作语义以纳入存储。表达式的求值结果通常取决于求值开始时的
存储内容，所以求值规则的参数不能只有项，还必须包含存储。项的求值又可能对
存储产生副作用，影响以后其他项的求值，因此规则还要返回新存储。于是，单步
求值关系由 \(t\trans t'\) 变成：
\[
t\mid\mu\trans t'\mid\mu',
\]
其中 \(\mu,\mu'\) 分别是存储的初始与最终状态。实际上，我们丰富了抽象机
的概念：机器状态不再只有程序计数器（用项表示），而是程序计数器加上存储的
当前内容。

为贯彻这一变化，先给所有已有求值规则加入存储。例如：
\[
\inferrule*[right=\textsc{E-AppAbs}]
 { }{(\lambda x:T_{11}.\,t_{12})\,v_2\mid\mu
 \trans\taplsubst{x}{v_2}{t_{12}}\mid\mu}
\]
\[
\inferrule*[right=\textsc{E-App1}]
 {t_1\mid\mu\trans t_1'\mid\mu'}
 {t_1\,t_2\mid\mu\trans t_1'\,t_2\mid\mu'}
\qquad
\inferrule*[right=\textsc{E-App2}]
 {t_2\mid\mu\trans t_2'\mid\mu'}
 {v_1\,t_2\mid\mu\trans v_1\,t_2'\mid\mu'}.
\]
第一条规则原样返回存储 \(\mu\)，因为函数应用本身没有副作用；另外两条只是
把前提中的副作用传播到结论。

接着稍微扩展项语法。求值 \(\mathsf{ref}\) 表达式会得到一个新鲜位置，所以
必须把位置纳入求值可能得到的结果，即值：
\[
\begin{array}{@{}rcll@{}}
v&::=&\lambda x:T.\,t&\text{值：抽象值}\\
 &\mid&\mathsf{unit}&\text{unit 值}\\
 &\mid&l&\text{存储位置}
\end{array}
\]
所有值也都是项，所以项集合也必须包括位置：
\[
\begin{array}{@{}rcll@{}}
t&::=&x&\text{项：变量}\\
 &\mid&\lambda x:T.\,t&\text{抽象}\\
 &\mid&t\ t&\text{应用}\\
 &\mid&\mathsf{unit}&\text{常量 unit}\\
 &\mid&\mathsf{ref}\ t&\text{创建引用}\\
 &\mid&!t&\text{解引用}\\
 &\mid&t:=t&\text{赋值}\\
 &\mid&l&\text{存储位置}
\end{array}
\]
当然，把具体位置加入项语法，不表示允许程序员直接书写含显式具体位置的项；
这类项只会作为求值中间结果出现。实际上，本章的项语言应当看成一种中间语言，
其中有些特性不直接开放给程序员。

在扩展后的语法上，可以陈述操纵位置与存储的新构造的求值规则。求值解引用
表达式 \(!t_1\) 时，先归约 \(t_1\) 直到它成为值：
\[
\inferrule*[right=\textsc{E-Deref}]
 {t_1\mid\mu\trans t_1'\mid\mu'}
 {!t_1\mid\mu\trans!t_1'\mid\mu'}.
\]
完成后应得到 \(!l\)，其中 \(l\) 是某个位置。试图解引用函数或 unit 等其他
值的项是错误的，求值规则会卡住；\S\ref{sec:13.5} 的类型安全性质保证
良类型项不会这样出错。
\[
\inferrule*[right=\textsc{E-DerefLoc}]
 {\mu(l)=v}{!l\mid\mu\trans v\mid\mu}.
\]

求值赋值表达式 \(t_1:=t_2\) 时，先求值 \(t_1\) 直到成为位置，再求值
\(t_2\) 直到成为任意种类的值：
\[
\inferrule*[right=\textsc{E-Assign1}]
 {t_1\mid\mu\trans t_1'\mid\mu'}
 {t_1:=t_2\mid\mu\trans t_1':=t_2\mid\mu'}
\]
\[
\inferrule*[right=\textsc{E-Assign2}]
 {t_2\mid\mu\trans t_2'\mid\mu'}
 {l:=t_2\mid\mu\trans l:=t_2'\mid\mu'}.
\]
两边都求值完后，表达式形如 \(l:=v_2\)，执行它就是更新存储，使 \(l\)
包含 \(v_2\)：
\[
\inferrule*[right=\textsc{E-Assign}]
 {l\in\dom(\mu)}
 {l:=v_2\mid\mu\trans\mathsf{unit}\mid[l\mapsto v_2]\mu}.
\]
记法 \([l\mapsto v_2]\mu\) 表示“把 \(l\) 映射到 \(v_2\)，其他位置的映射
与 \(\mu\) 相同的存储”。这一步所得项只是 \(\mathsf{unit}\)；有意思的
结果是更新后的存储。

最后，求值 \(\mathsf{ref}\ t_1\) 时，先把 \(t_1\) 求值为值：
\[
\inferrule*[right=\textsc{E-Ref}]
 {t_1\mid\mu\trans t_1'\mid\mu'}
 {\mathsf{ref}\ t_1\mid\mu\trans\mathsf{ref}\ t_1'\mid\mu'}.
\]
然后选择新鲜位置 \(l\)，即 \(l\notin\dom(\mu)\)，产生以新绑定
\(l\mapsto v_1\) 扩展 \(\mu\) 的存储：
\[
\inferrule*[right=\textsc{E-RefV}]
 {l\notin\dom(\mu)}
 {\mathsf{ref}\ v_1\mid\mu\trans l\mid(\mu,l\mapsto v_1)}.
\]
这一步所得项就是新分配位置的名字 \(l\)。

这些规则没有执行任何垃圾回收：求值过程中，存储可以无界增长。这不影响求值
结果的正确性——“垃圾”按定义正是存储中已无法到达、不会再对求值发挥作用的
部分——但意味着朴素求值器有时会耗尽内存，而更复杂的求值器本可重用内容
已经成为垃圾的位置并继续运行。

\begin{exercise}[\(\star\star\star\)]
\label{ex:13.3.1}
可以怎样细化求值规则，以模拟垃圾回收？还需要证明什么定理，才能论证这种
细化是正确的？
\end{exercise}

\section{存储类型}
\label{sec:13.4}

语法和求值规则已经扩展为容纳引用，最后要写下新构造的类型规则，并检查它们
可靠。关键问题自然是：“位置具有什么类型？”

求值含具体位置的项时，结果类型取决于初始存储的内容。例如，在存储
\((l_1\mapsto\mathsf{unit},l_2\mapsto\mathsf{unit})\) 中求值
\(!l_2\)，结果是 \(\mathsf{unit}\)；在存储
\((l_1\mapsto\mathsf{unit},
l_2\mapsto\lambda x:\tapltype{Unit}.\,x)\) 中求值同一个项，结果是
\(\lambda x:\tapltype{Unit}.\,x\)。相对于前一存储，\(l_2\) 的内容类型
为 \(\tapltype{Unit}\)；相对于后一存储，它的内容类型为
\(\tapltype{Unit}\to\tapltype{Unit}\)。由此立即得到第一版位置类型规则：
\[
\inferrule
 {\mu(l)=v_1\\\Gamma\mid\mu\vdash v_1:T_1}
 {\Gamma\mid\mu\vdash l:\tapltype{Ref}\ T_1}.
\]
也就是说，要找位置 \(l\) 的类型，就在存储中查找 \(l\) 的当前内容，再
计算内容的类型 \(T_1\)；位置的类型就是 \(\tapltype{Ref}\ T_1\)。

这样开始之后，还要再前进一步才能得到一致的系统。让项的类型依赖存储，实际
已经把类型关系从上下文、项、类型之间的三元关系，改成了上下文、存储、项、
类型之间的四元关系。直觉上，存储是计算项类型之上下文的一部分，因此把这个
四元关系写成 \(\Gamma\mid\mu\vdash t:T\)，将存储放在转门左侧。所有其他
类型规则也类似地加入存储；它们无需对存储作任何有意思的操作，只把存储从
前提传到结论。

但上述规则有两个问题。第一，类型检查效率很低，因为计算位置 \(l\) 的类型
需要计算其当前内容 \(v\) 的类型。若 \(l\) 在项 \(t\) 中出现多次，构造
\(t\) 的类型推导时就会重复计算 \(v\) 的类型。若 \(v\) 自己还含位置，
每次出现又要重算它们的类型。例如，存储若含有：
\[
\begin{aligned}
(&l_1\mapsto\lambda x:\tapltype{Nat}.\,999,\\
 &l_2\mapsto\lambda x:\tapltype{Nat}.\,(!l_1)\,x,\\
 &l_3\mapsto\lambda x:\tapltype{Nat}.\,(!l_2)\,x,\\
 &l_4\mapsto\lambda x:\tapltype{Nat}.\,(!l_3)\,x,\\
 &l_5\mapsto\lambda x:\tapltype{Nat}.\,(!l_4)\,x),
\end{aligned}
\]
计算 \(l_5\) 的类型就涉及依次计算 \(l_4,l_3,l_2,l_1\) 的类型。

第二，若存储含有环，建议的规则可能根本无法导出任何结果。例如相对于存储：
\[
(l_1\mapsto\lambda x:\tapltype{Nat}.\,(!l_2)\,x,\quad
 l_2\mapsto\lambda x:\tapltype{Nat}.\,(!l_1)\,x),
\]
\(l_2\) 不存在有限类型推导，因为计算 \(l_2\) 的类型需要先找 \(l_1\) 的
类型，而后者又涉及 \(l_2\)，如此往复。环形引用结构在实践中确实会出现，
例如可以构造双向链表；我们希望类型系统能处理它们。

\begin{exercise}[\(\star\)]
\label{ex:13.4.1}
能否找出一个项，其求值会生成上面这个特定的环形存储？
\end{exercise}

两个问题都来自建议的规则要求每次在项中提及位置时重新计算其类型。但直觉上
没有这个必要。位置刚创建时，我们知道存入其中的初值类型；以后虽然可能向该
位置存入其他值，它们却总会与初值具有相同类型。换言之，我们心中始终为存储
中的每个位置保留一个确定类型，并且在位置分配时便固定下来。可以把这些预期
类型收集成\termfirst{存储类型}{store typing}，即从位置到类型的有限函数。
用元变量 \(\Sigma\) 表示这类函数。

若给定存储类型 \(\Sigma\)，描述项 \(t\) 将在哪个存储 \(\mu\) 中求值，
就可以只用 \(\Sigma\) 计算 \(t\) 的结果类型，完全不必直接查看 \(\mu\)。
例如，若
\(\Sigma=(l_1\mapsto\tapltype{Unit},
l_2\mapsto\tapltype{Unit}\to\tapltype{Unit})\)，便能立即推断
\(!l_2:\tapltype{Unit}\to\tapltype{Unit}\)。一般地，位置的类型规则改写
为：
\[
\inferrule*[right=\textsc{T-Loc}]
 {\Sigma(l)=T_1}
 {\Gamma\mid\Sigma\vdash l:\tapltype{Ref}\ T_1}.
\]
类型仍是四元关系，但现在以存储类型而不是具体存储为参数。其余类型规则也
类似地加入存储类型。

当然，只有求值实际使用的具体存储确实符合类型检查时假定的存储类型，这些
规则才能准确预测求值结果。这个条件与此前所有演算中的自由变量完全平行：
替换引理~\ref{lem:9.3.8} 保证，若 \(\Gamma\vdash t:T\)，就能用
\(\Gamma\) 中列出的相应类型之值替换 \(t\) 的自由变量，得到类型为 \(T\)
的闭项；再由类型保持性定理~\ref{thm:9.3.9}，若它产生结果，最终结果仍
具有类型 \(T\)。\S\ref{sec:13.5} 会形式化存储与存储类型之间类似的直觉。

最后，检查程序员实际书写的项时，不必费力猜测该用什么存储类型。具体位置
常量只会出现在求值的中间结果中，不属于程序员书写的语言。因此，只需相对于
空存储类型检查程序员的项。求值过程中创建新位置时，根据放入新单元的初值
类型，总能看出怎样扩展存储类型；下面的保持性定理~\ref{thm:13.5.3} 会
形式化这一直觉。

处理完位置后，其他新句法形式的类型规则都很直接。对 \(T_1\) 型值创建的
引用具有类型 \(\tapltype{Ref}\ T_1\)：
\[
\inferrule*[right=\textsc{T-Ref}]
 {\Gamma\mid\Sigma\vdash t_1:T_1}
 {\Gamma\mid\Sigma\vdash\mathsf{ref}\ t_1:\tapltype{Ref}\ T_1}.
\]
这里不需要扩展存储类型，因为新位置的名字到运行时才会确定，而 \(\Sigma\)
只记录已经分配的存储单元与其类型的联系。

反过来，若 \(t_1\) 求值为 \(\tapltype{Ref}\ T_{11}\) 型的位置，对它
解引用保证产生 \(T_{11}\) 型的值：
\[
\inferrule*[right=\textsc{T-Deref}]
 {\Gamma\mid\Sigma\vdash t_1:\tapltype{Ref}\ T_{11}}
 {\Gamma\mid\Sigma\vdash!t_1:T_{11}}.
\]
最后，若 \(t_1\) 表示 \(T_{11}\) 型单元，只要 \(t_2\) 的类型也是
\(T_{11}\)，就能把它存入该单元：
\[
\inferrule*[right=\textsc{T-Assign}]
 {\Gamma\mid\Sigma\vdash t_1:\tapltype{Ref}\ T_{11}\\
  \Gamma\mid\Sigma\vdash t_2:T_{11}}
 {\Gamma\mid\Sigma\vdash t_1:=t_2:\tapltype{Unit}}.
\]

\section{安全性}
\label{sec:13.5}

最后要检查，引用演算仍然满足标准类型安全性质。进展性定理——良类型项不会
卡住——几乎可以照旧陈述和证明，见定理~\ref{thm:13.5.7}；只需在证明中
为新构造增加几个直接的情形。保持性定理略有意思，所以先考察它。

求值关系已经加入初始、最终存储，类型关系也加入存储类型，因此保持性的陈述
必须包含这些参数。但显然不能只把存储与存储类型塞进去，却完全不说明它们
怎样联系：
\[
\text{若 }\Gamma\mid\Sigma\vdash t:T
\text{ 且 }t\mid\mu\trans t'\mid\mu',
\text{ 则 }\Gamma\mid\Sigma\vdash t':T.
\qquad\text{（错误！）}
\]
若类型检查依据的是一组关于存储值类型的假设，求值却使用违反这些假设的
存储，结果必然是灾难。下面的要求表达所需约束。

\begin{definition}
\label{def:13.5.1}
若 \(\dom(\mu)=\dom(\Sigma)\)，并且对每个
\(l\in\dom(\mu)\) 都有
\(\Gamma\mid\Sigma\vdash\mu(l):\Sigma(l)\)，则称存储 \(\mu\) 相对于
类型上下文 \(\Gamma\) 与存储类型 \(\Sigma\) 是
\termfirst{良类型的}{well typed}，记作
\(\Gamma\mid\Sigma\vdash\mu\)。
\end{definition}

直觉上，若存储中的每个值都具有存储类型所预测的类型，存储 \(\mu\) 就与
存储类型 \(\Sigma\) 一致。

\translatornote{作者勘误指出，针对本章实际只求值闭程序的用途，这里也可以
固定为空类型上下文，而不允许任意 \(\Gamma\)。原书采用的较一般陈述仍是
正确的，本译文保留它，以便与随后各引理和定理的统一记法对应。}

\begin{exercise}[\(\star\star\)]
\label{ex:13.5.2}
能否找出上下文 \(\Gamma\)、存储 \(\mu\) 以及两个不同的存储类型
\(\Sigma_1,\Sigma_2\)，使
\(\Gamma\mid\Sigma_1\vdash\mu\) 与
\(\Gamma\mid\Sigma_2\vdash\mu\) 都成立？
\end{exercise}

现在可以陈述一项更接近目标的保持性质：
\[
\left.
\begin{array}{l}
\Gamma\mid\Sigma\vdash t:T\\
t\mid\mu\trans t'\mid\mu'\\
\Gamma\mid\Sigma\vdash\mu
\end{array}\right\}
\quad\Longrightarrow\quad
\Gamma\mid\Sigma\vdash t':T.
\qquad\text{（仍不够正确。）}
\]
这对除分配规则 \textsc{E-RefV} 外的所有求值规则都没有问题。问题在于，
该规则产生的存储定义域大于初始存储；上述陈述的结论会失效：若 \(\mu'\)
包含新鲜位置 \(l\) 的绑定，\(l\) 不可能属于 \(\Sigma\) 的定义域，而
且明确提到 \(l\) 的 \(t'\) 不能在 \(\Sigma\) 下赋型。

存储在求值过程中可能增长，显然也必须允许存储类型增长。于是得到保持性的
最终正确陈述。

\begin{theorem}[保持性]
\label{thm:13.5.3}
若
\[
\Gamma\mid\Sigma\vdash t:T,\qquad
\Gamma\mid\Sigma\vdash\mu,\qquad
t\mid\mu\trans t'\mid\mu',
\]
则存在某个 \(\Sigma'\supseteq\Sigma\)，使
\[
\Gamma\mid\Sigma'\vdash t':T
\qquad\text{且}\qquad
\Gamma\mid\Sigma'\vdash\mu'.
\]
\end{theorem}

这里的 \(\Sigma'\supseteq\Sigma\) 表示 \(\Sigma'\) 对所有旧位置的
\emph{类型}都与 \(\Sigma\) 一致。保持性定理只断言存在某个这样的存储类型
\(\Sigma'\)，使新项 \(t'\) 在它之下为良类型；没有精确指出
\(\Sigma'\) 是什么。直觉上当然清楚，\(\Sigma'\) 要么就是 \(\Sigma\)，
要么恰好是 \(\Sigma,l\mapsto T_1\)，其中 \(l\) 是新分配的位置
（\(\mu'\) 定义域中的新元素），\(T_1\) 是扩展后存储
\(\mu,l\mapsto v_1\) 中绑定到 \(l\) 的初值类型。但显式写进定理会使陈述
复杂，却不会更有用；上面的较弱版本已经具有适当形式——其结论又能作为
假设——因而可以反复“转动曲柄”，推出任意求值步序列都保持良类型性。再与
进展性质结合，就得到通常的保证：“良类型程序永不出错。”

证明保持性需要几个技术引理。第一个是标准替换引理
\ref{lem:9.3.8} 的简单扩展。

\begin{lemma}[替换]
\label{lem:13.5.4}
若 \(\Gamma,x:S\mid\Sigma\vdash t:T\)，且
\(\Gamma\mid\Sigma\vdash s:S\)，则
\(\Gamma\mid\Sigma\vdash\taplsubst{x}{s}{t}:T\)。
\end{lemma}

\begin{proof}
与引理~\ref{lem:9.3.8} 相同。
\end{proof}

下一个引理说明，以类型适当的新值替换存储中一个单元的内容，不会改变存储
整体的类型。

\begin{lemma}
\label{lem:13.5.5}
若
\[
\Gamma\mid\Sigma\vdash\mu,\qquad
\Sigma(l)=T,\qquad
\Gamma\mid\Sigma\vdash v:T,
\]
则 \(\Gamma\mid\Sigma\vdash[l\mapsto v]\mu\)。
\end{lemma}

\begin{proof}
由 \(\Gamma\mid\Sigma\vdash\mu\) 的定义立即得到。
\end{proof}

最后还需要存储的一种弱化引理：若以新位置扩展存储，扩展后的存储仍允许为
原存储能赋型的所有项指派类型。

\begin{lemma}
\label{lem:13.5.6}
若 \(\Gamma\mid\Sigma\vdash t:T\)，且
\(\Sigma'\supseteq\Sigma\)，则
\(\Gamma\mid\Sigma'\vdash t:T\)。
\end{lemma}

\begin{proof}
作简单归纳。
\end{proof}

\begin{proof}[定理~\ref{thm:13.5.3} 的证明]
对求值推导作直接归纳，使用上述引理以及类型规则的反演性质
（引理~\ref{lem:9.3.1} 的直接扩展）。
\end{proof}

进展性定理~\ref{thm:9.3.5} 的陈述也必须扩展，以纳入存储与存储类型。

\begin{theorem}[进展性]
\label{thm:13.5.7}
设 \(t\) 是闭的良类型项，即对某个 \(T,\Sigma\) 有
\(\varnothing\mid\Sigma\vdash t:T\)。那么，\(t\) 要么是值，要么对每个
满足 \(\varnothing\mid\Sigma\vdash\mu\) 的存储 \(\mu\)，都存在项 \(t'\)
和存储 \(\mu'\)，使
\[
t\mid\mu\trans t'\mid\mu'.
\]
\end{theorem}

\begin{proof}
沿定理~\ref{thm:9.3.5} 的模式，对类型推导作直接归纳。典范形式引理
\ref{lem:9.3.4} 需要再增加两种情形：类型
\(\tapltype{Ref}\ T\) 的所有值都是位置，
\(\tapltype{Unit}\) 的所有值都是 \(\mathsf{unit}\)。
\end{proof}

\begin{exercise}[推荐，\(\star\star\star\)]
\label{ex:13.5.8}
本章的求值关系在良类型项上可规范化吗？若是，请证明；若不是，请在当前演算
加入自然数和布尔值后，写出一个良类型的阶乘函数。
\end{exercise}

\section{注记}
\label{sec:13.6}

本章呈现改编自 Harper（1994、1996）的处理；Wright 与 Felleisen（1994）
也给出了风格相似的论述。

引用（或其他计算效应）与 ML 风格多态类型推断结合时，会产生颇为微妙的
问题（见 \taplsecref{22.7}{sec:22.7}），在研究文献中受到广泛关注。
参见 Tofte
（1990）、Hoang 等（1993）、Jouvelot 与 Gifford（1991）、Talpin 与
Jouvelot（1992）、Leroy 与 Weis（1991）、Wright（1992）、Harper
（1994、1996）及其中所引资料。

静态预测可能出现的别名，是编译器实现与程序语言理论中由来已久的问题；在
编译器中称为\termfirst{别名分析}{alias analysis}。Reynolds（1978、
1989）早期一项影响深远的尝试创造了
\termfirst{干扰的句法控制}{syntactic control of interference}一词。
这些思想近年来再次活跃，参见 O'Hearn 等（1995）与 Smith 等（2000）。
更一般的别名推理技术见 Reynolds（1981）、Ishtiaq 与 O'Hearn（2001）
及其中引用的其他资料。

Jones 与 Lins（1996）全面讨论了垃圾回收；Morrisett 等（1995）给出更偏
语义的处理。

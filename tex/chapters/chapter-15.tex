\chapter{子类型化}
\label{chap:15}

过去几章一直在简单类型 lambda 演算的框架中研究各种语言特性的类型行为。
本章加入一项更基础的扩展：\termfirst{子类型化}{subtyping}，有时也称
\termfirst{子类型多态}{subtype polymorphism}。此前的许多特性大体可以彼此
独立地加入语言，子类型化却会横贯整个类型系统，并以并不简单的方式与多数
其他语言特性相互作用。

子类型化常见于面向对象语言，也常被视为面向对象风格的核心特性。\chapref{18}
将详细讨论这层联系。本章先在一个只含函数和记录的精简语言中介绍子类型化；
这样的框架已经足以呈现大多数关键问题。\footnote{本章研究带子类型化
（\cref{fig:15-1}）和记录（\cref{fig:15-3}）的简单类型 lambda 演算
\(\lambda_{<:}\)。对应的 OCaml 实现是 \texttt{rcdsub}；含自然数的例子
需要用 \texttt{fullsub} 检查。}\taplsecref{15.5}{sec:15.5}讨论它与前几章若干特性的
组合，\taplsecref{15.6}{sec:15.6}则考察一种更精细的语义：把子类型化的使用
翻译成运行时强制转换。

\section{包容规则}
\label{sec:15.1}

没有子类型化时，简单类型 lambda 演算的规则有时显得过于僵硬。类型系统要求
实参类型与函数的参数类型完全相同，因而会拒绝不少程序员看来显然不会出错的
程序。回顾函数应用的类型规则：
\[
\inferrule*[right=\textsc{T-App}]
 {\Gamma\vdash t_1:T_{11}\to T_{12}\\
  \Gamma\vdash t_2:T_{11}}
 {\Gamma\vdash t_1\,t_2:T_{12}}
\]
按照这条规则，行为良好的项
\[
(\lambda r:\{x:\tapltype{Nat}\}.\,r.x)\ \{x=0,y=1\}
\]
无法赋型：实参的类型是
\(\{x:\tapltype{Nat},y:\tapltype{Nat}\}\)，函数却要求
\(\{x:\tapltype{Nat}\}\)。然而，函数只需要实参含有一个类型为
\(\tapltype{Nat}\) 的字段 \(x\)，并不关心是否还含有其他字段。从函数的
类型就能看出这一点，不必检查函数体。因此，把
\(\{x:\tapltype{Nat},y:\tapltype{Nat}\}\) 类型的实参传给要求
\(\{x:\tapltype{Nat}\}\) 的函数总是安全的。

子类型化的目标，就是让类型规则接受这样的项。若类型 \(S\) 比 \(T\) 提供
更多信息，我们称 \(S\) 是 \(T\) 的子类型，写作
\(S\subtype T\)。它的含义是：任何类型为 \(S\) 的项，都能安全地用于本来
需要 \(T\) 型项的上下文。这种理解常称为
\termfirst{安全替换原则}{principle of safe substitution}。

还可以把 \(S\subtype T\) 读作“\(S\) 所描述的每个值也都由 \(T\) 描述”，
也就是“\(S\) 的元素集合是 \(T\) 的元素集合的子集”。
\taplsecref{15.6}{sec:15.6}会看到，子类型化有时还适合采用更精细的解释；
在多数场合，这种\termfirst{子集语义}{subset semantics}已经足够。

类型关系与子类型关系由一条新的类型规则连接起来，这就是
\termfirst{包容规则}{rule of subsumption}：
\[
\inferrule*[right=\textsc{T-Sub}]
 {\Gamma\vdash t:S\\S\subtype T}
 {\Gamma\vdash t:T}
\]
若 \(S\subtype T\)，这条规则允许把每个 \(S\) 型项也当作 \(T\) 型项。
例如，一旦规定
\(\{x:\tapltype{Nat},y:\tapltype{Nat}\}\subtype
\{x:\tapltype{Nat}\}\)，就能由 \textsc{T-Sub} 得到
\(\vdash\{x=0,y=1\}:\{x:\tapltype{Nat}\}\)，从而为开头的例子赋型。

\section{子类型关系}
\label{sec:15.2}

子类型关系由一组推导 \(S\subtype T\) 的推理规则形式化。这个判断读作
“\(S\) 是 \(T\) 的子类型”，也可以说“\(T\) 是 \(S\) 的超类型”。我们分别
处理函数类型、记录类型等各种类型形式，为每种形式规定：何时可以把一种类型
的元素安全地用于需要另一种类型的地方。

在讨论具体的类型构造子之前，先作两项一般规定。子类型关系具有自反性和传递性：
\[
\inferrule*[right=\textsc{S-Refl}]{ }{S\subtype S}
\qquad
\inferrule*[right=\textsc{S-Trans}]
 {S\subtype U\\U\subtype T}{S\subtype T}
\]
这两条规则都直接来自安全替换原则。

先看记录。设
\(S=\{k_j:S_j\}^{j\in1..m}\)，
\(T=\{l_i:T_i\}^{i\in1..n}\)。如果 \(T\) 的字段少于 \(S\)，我们希望
把 \(S\) 看作 \(T\) 的子类型。特别地，从记录类型末尾“忘掉”若干字段是
安全的。这由\termfirst{宽度子类型规则}{width subtyping rule}表达：
\[
\inferrule*[right=\textsc{S-RcdWidth}]
 { }{
 \{l_i:T_i\}^{i\in1..n+m}\subtype
 \{l_i:T_i\}^{i\in1..n}}
\]
字段更多的类型反而是“更小”的子类型，乍看似乎反常。可以沿用
\taplsecref{11.8}{sec:11.8}的记录类型，并对它采取更宽松的解释：
\(\{x:\tapltype{Nat}\}\) 描述所有“至少含有一个
\(\tapltype{Nat}\) 型字段 \(x\)”的记录。因此，\(\{x=3\}\)、
\(\{x=5\}\)、\(\{x=3,y=100\}\) 和
\(\{x=3,a=\tapltrue,b=\tapltrue\}\) 都属于该类型。相比之下，
\(\{x:\tapltype{Nat},y:\tapltype{Nat}\}\) 还要求字段 \(y\)，所描述的
值更少。例如，\(\{x=3,y=100\}\) 和
\(\{x=3,y=100,z=\tapltrue\}\) 属于这个类型，\(\{x=3\}\) 和
\(\{x=3,a=\tapltrue,b=\tapltrue\}\) 则不属于。字段更多的记录类型提出了更严格、信息量
更大的要求，因而描述更小的值集合。

宽度规则要求两边共有字段的类型完全相同。还可以进一步放宽这一要求：只要两个
记录中各对应字段的类型满足子类型关系，共有字段的类型就不必完全相同。
\termfirst{深度子类型规则}{depth subtyping rule}表达这一点：
\[
\inferrule*[right=\textsc{S-RcdDepth}]
 {S_i\subtype T_i\quad(\text{对每个 }i\in1..n)}
 {\{l_i:S_i\}^{i\in1..n}\subtype
  \{l_i:T_i\}^{i\in1..n}}
\]
例如，结合宽度与深度规则可以推得：
\[
\inferrule*[right=\textsc{S-RcdDepth}]
 {\inferrule*[right=\textsc{S-RcdWidth}]
   { }{\{a:\tapltype{Nat},b:\tapltype{Nat}\}\subtype
       \{a:\tapltype{Nat}\}}\\
  \inferrule*[right=\textsc{S-RcdWidth}]
   { }{\{m:\tapltype{Nat}\}\subtype\{\}}}
 {\{x:\{a:\tapltype{Nat},b:\tapltype{Nat}\},
       y:\{m:\tapltype{Nat}\}\}
  \subtype
  \{x:\{a:\tapltype{Nat}\},y:\{\}\}}
\]
若只想改变一个字段，可对其他字段用 \textsc{S-Refl} 构造平凡的子类型推导。
还可以用 \textsc{S-Trans} 拼接宽度与深度推导，在提升一个字段类型的同时
丢掉另一个字段。

最后，记录一旦构造完成，安全使用它的基本操作只有字段投影，而字段投影不受
字段排列次序影响。因此得到
\termfirst{排列子类型规则}{permutation subtyping rule}：
\[
\inferrule*[right=\textsc{S-RcdPerm}]
 {\{k_j:S_j\}^{j\in1..n}\text{ 是 }
   \{l_i:T_i\}^{i\in1..n}\text{ 的一个排列}}
 {\{k_j:S_j\}^{j\in1..n}\subtype
  \{l_i:T_i\}^{i\in1..n}}
\]
例如，\textsc{S-RcdPerm} 同时给出
\(\{c:\tapltype{Bool},b:\tapltype{Bool},a:\tapltype{Nat}\}\subtype
\{a:\tapltype{Nat},b:\tapltype{Bool},c:\tapltype{Bool}\}\) 及其反向
关系。这也说明子类型关系不具有反对称性。把排列、宽度和传递规则结合起来，
就能丢掉记录类型中任意位置的字段。

\label{ex:15.2.1}

\(\{x:\tapltype{Nat},y:\tapltype{Nat},z:\tapltype{Nat}\}\subtype

\end{exercise}

宽度、深度和排列规则分别表达记录使用中的三种灵活性。为了说明概念，把它们
分成三条规则很有帮助；有些语言确实只允许其中一部分。例如，Abadi 与
Cardelli（1996）提出的对象演算有多个变体，其中大多数不采用深度子类型化。
实际实现时，把三者合并成一条同时处理宽度、深度和排列的宏规则更为方便；
\chapref{16}将采用这种做法。

因为当前语言是高阶语言，函数本身也可以作为参数传递，所以还必须规定函数
类型之间何时存在子类型关系：
\[
\inferrule*[right=\textsc{S-Arrow}]
 {T_1\subtype S_1\\S_2\subtype T_2}
 {S_1\to S_2\subtype T_1\to T_2}
\]
其中，参数类型的前提 \(T_1\subtype S_1\) 与结论
\(S_1\to S_2\subtype T_1\to T_2\) 中的子类型方向相反，称为参数类型上的
\termfirst{逆变}{contravariance}；结果类型的前提 \(S_2\subtype T_2\)
与结论中的方向相同，\mbox{称为\termfirst{协变}{covariance}}。若函数
\(f:S_1\to S_2\)，它能接收每个
\(S_1\) 型值，自然也能接收 \(S_1\) 的任意子类型 \(T_1\) 的值；它返回
\(S_2\) 型值，这些结果也可以被看作任意超类型 \(T_2\) 的值。因此，
\(f\) 也能具有类型 \(T_1\to T_2\)。换一种说法，传给函数的任何实参都
不能超出它的接收能力（\(T_1\subtype S_1\)），函数返回的任何结果也不能
超出上下文的接收能力（\(S_2\subtype T_2\)）。

\translatornote{把类型理解为它所包含的值的集合。若
\(T_1\subtype S_1\)，就有
\(\sembracket{T_1}\subseteq\sembracket{S_1}\)。固定结果
类型 \(U\) 后，\(S_1\to U\) 型函数必须能处理集合
\(\sembracket{S_1}\) 中的每个输入；\(T_1\to U\) 型函数只须处理
较小集合 \(\sembracket{T_1}\) 中的输入。前一条件更严格，因此满足
它的函数也一定满足后一条件，即
\(\sembracket{S_1\to U}\subseteq\sembracket{T_1\to U}\)，从而
\(S_1\to U\subtype T_1\to U\)。换言之，能处理 \(S_1\) 中所有输入的
函数，一定也能处理其子集 \(T_1\) 中的所有输入；反过来则未必。因此，
\(S_1\to U\) 型函数都属于 \(T_1\to U\)，参数位置上的子类型方向由此发生
反转。}

最后，引入最大类型 \(\tapltype{Top}\)，并规定每个类型都是它的子类型：
\[
\inferrule*[right=\textsc{S-Top}]{ }{S\subtype\tapltype{Top}}
\]
\taplsecref{15.4}{sec:15.4}还会讨论这个类型。

形式上，子类型关系是由上述规则闭合生成的最小关系。自反性与传递性使它成为
预序；记录排列规则又使不同类型可能互为子类型，所以它不是偏序。

\section{子类型关系与类型关系的性质}
\label{sec:15.3}

确定带子类型化的 lambda 演算后，还要验证定义确实合理，特别是简单类型
lambda 演算的保持性和进展性在加入子类型化后仍然成立。

\begin{exercise}[推荐，\(\star\star\)]
\label{ex:15.3.1}
继续阅读前，先预测可能在哪里遇到困难。假设定义子类型关系时误加了一条不
正确的规则，系统的哪些性质可能失效？反过来，如果删去一条子类型规则，是否
也会破坏某些性质？
\end{exercise}
\taplauthorsolutionlink{sol:author:15.3.1}{15.3.1}

下面先给出子类型关系的一项关键性质；它与简单类型 lambda 演算中类型关系的
反演引理（\cref{lem:9.3.1}）相对应。若 \(S\) 是某个箭头类型的子类型，子类型
反演引理说明 \(S\) 本身也必须是箭头类型，并给出两个参数类型间的逆变关系
与两个结果类型间的协变关系。对于记录类型，若
\(S\subtype\{l_i:T_i\}^{i\in1..n}\)，类似结论说明 \(S\) 至少含有
\(\{l_i:T_i\}^{i\in1..n}\) 列出的所有字段；字段可以采用不同次序，共有
字段的类型满足子类型关系。

\taplstatementliststart
\begin{lemma}[子类型关系的反演]
\label{lem:15.3.2}
\taplstatementlistbreak
\begin{enumerate}
\item 若 \(S\subtype T_1\to T_2\)，则
  \(S=S_1\to S_2\)，且 \(T_1\subtype S_1\)、\(S_2\subtype T_2\)。
\item 若 \(S\subtype\{l_i:T_i\}^{i\in1..n}\)，则
  \(S=\{k_j:S_j\}^{j\in1..m}\)，并且
  \(\{l_i\mid i\in1..n\}\subseteq\{k_j\mid j\in1..m\}\)；
  对每对相同标签 \(l_i=k_j\)，都有 \(S_j\subtype T_i\)。
\end{enumerate}
\end{lemma}
\begin{proof}
练习（推荐，\(\star\star\)）。
\end{proof}

\taplauthorsolutionlink{sol:author:15.3.2}{15.3.2}

为证明求值保持类型，先给出类型关系的反演引理。这里只列保持性证明实际需要
的两个情形；更一般的形式可以从下一章的算法类型关系
（\cref{def:16.2.2}）读出。

\taplstatementliststart
\begin{lemma}
\label{lem:15.3.3}
\taplstatementlistbreak
\begin{enumerate}
\item 若 \(\Gamma\vdash\lambda x:S_1.\,s_2:T_1\to T_2\)，则
  \(T_1\subtype S_1\)，且 \(\Gamma,x:S_1\vdash s_2:T_2\)。
\item 若
  \(\Gamma\vdash\{k_a=s_a\}^{a\in1..m}:\{l_i:T_i\}^{i\in1..n}\)，
  则类型中列出的每个标签 \(l_i\) 都出现在记录项的标签 \(k_a\) 中，即
  \(\{l_i\}^{i\in1..n}\subseteq\{k_a\}^{a\in1..m}\)；对每对相同标签
  \(k_a=l_i\)，都有 \(\Gamma\vdash s_a:T_i\)。
\end{enumerate}
\end{lemma}
\begin{proof}
对类型推导作直接归纳；末条规则为 \textsc{T-Sub} 时使用
\cref{lem:15.3.2}。
\end{proof}

接着需要类型关系的替换引理。它的陈述与简单类型 lambda 演算中的
\cref{lem:9.3.8}相同，证明也几乎一致。

\begin{lemma}[替换]
\label{lem:15.3.4}
若 \(\Gamma,x:S\vdash t:T\) 且 \(\Gamma\vdash s:S\)，则
\(\Gamma\vdash\taplsubst{x}{s}{t}:T\)。
\end{lemma}
\begin{proof}
对给定类型推导的深度作归纳。新增的 \textsc{T-Sub}、\textsc{T-Rcd} 和
\textsc{T-Proj} 情形直接使用归纳假设，其余与\cref{lem:9.3.8}相同。
\end{proof}

保持性定理的陈述仍与以前相同，不过证明中的若干地方需要处理子类型化。

\begin{theorem}[保持性]
\label{thm:15.3.5}
若 \(\Gamma\vdash t:T\) 且 \(t\trans t'\)，则
\(\Gamma\vdash t':T\)。
\end{theorem}
\begin{proof}
对给定类型推导的深度作归纳，并按最后一条类型规则分类。多数情形与
\cref{thm:9.3.9}相同；这里只写新增或需要子类型化的情形。

\emph{情形 \textsc{T-Var}。}变量没有求值规则，不可能发生。

\emph{情形 \textsc{T-Abs}。}lambda 抽象已经是值，不可能发生。

\emph{情形 \textsc{T-App}。}已知
\(t=t_1\,t_2\)、\(\Gamma\vdash t_1:T_{11}\to T_{12}\)、
\(\Gamma\vdash t_2:T_{11}\)，且 \(T=T_{12}\)。求值末条规则可能是
\textsc{E-App1}、\textsc{E-App2} 或 \textsc{E-AppAbs}。前两种由归纳
假设和 \textsc{T-App} 立即得到。若为 \textsc{E-AppAbs}，则
\(t_1=\lambda x:S_{11}.\,t_{12}\)、\(t_2=v_2\)，且
\(t'=\taplsubst{x}{v_2}{t_{12}}\)。由\cref{lem:15.3.3}第 1 项得到
\(T_{11}\subtype S_{11}\) 和
\(\Gamma,x:S_{11}\vdash t_{12}:T_{12}\)。由 \textsc{T-Sub} 得
\(\Gamma\vdash v_2:S_{11}\)，再由替换引理得到
\(\Gamma\vdash t':T_{12}\)。

\emph{情形 \textsc{T-Rcd}。}记录只能由 \textsc{E-Rcd} 求值。设第
\(j\) 个字段从 \(t_j\) 变为 \(t_j'\)。对相应前提
\(\Gamma\vdash t_j:T_j\) 使用归纳假设，再用 \textsc{T-Rcd} 重建整条
记录的类型推导。

\emph{情形 \textsc{T-Proj}。}若末条求值规则为 \textsc{E-Proj}，由归纳
假设和 \textsc{T-Proj} 得证。若为 \textsc{E-ProjRcd}，则
\(t_1=\{k_a=v_a\}^{a\in1..m}\)、\(l_j=k_b\)，且 \(t'=v_b\)。由
\cref{lem:15.3.3}第 2 项，类型 \(\{l_i:T_i\}^{i\in1..n}\) 要求的标签都
出现在 \(t_1\) 中，并且
相同标签对应的值具有所需字段类型；特别地，\(\Gamma\vdash v_b:T_j\)。

\emph{情形 \textsc{T-Sub}。}由前提得
\(\Gamma\vdash t:S\) 和 \(S\subtype T\)。归纳假设给出
\(\Gamma\vdash t':S\)，再由 \textsc{T-Sub} 得
\(\Gamma\vdash t':T\)。
\end{proof}

证明进展性之前，仍先给出典范形式引理，说明箭头类型和记录类型的闭值只能
采用哪些形式。

\taplstatementliststart
\begin{lemma}[典范形式]
\label{lem:15.3.6}
\taplstatementlistbreak
\begin{enumerate}
\item 若闭值 \(v\) 具有类型 \(T_1\to T_2\)，则
  \(v=\lambda x:S_1.\,t_2\)。
\item 若闭值 \(v\) 具有类型 \(\{l_i:T_i\}^{i\in1..n}\)，则
  \(v=\{k_a=v_a\}^{a\in1..m}\)，且类型
  \(\{l_i:T_i\}^{i\in1..n}\) 中列出的每个标签都出现在该记录值中。
\end{enumerate}
\end{lemma}
\begin{proof}
练习（推荐，\(\star\star\star\)）。
\end{proof}
\taplauthorsolutionlink{sol:author:15.3.6}{15.3.6}

\begin{theorem}[进展性]
\label{thm:15.3.7}
若 \(t\) 是闭的良类型项，则 \(t\) 要么是值，要么存在 \(t'\) 使
\(t\trans t'\)。
\end{theorem}
\begin{proof}
对类型推导作直接归纳。变量情形因 \(t\) 是闭项而不可能发生；lambda 抽象
本身就是值。

\emph{情形 \textsc{T-App}。}分别对 \(t_1\) 和 \(t_2\) 使用归纳假设。
若 \(t_1\) 能求值，使用 \textsc{E-App1}；若 \(t_1\) 已是值而 \(t_2\)
能求值，使用 \textsc{E-App2}。若二者都是值，\cref{lem:15.3.6}说明
\(t_1\) 是 lambda 抽象，于是 \textsc{E-AppAbs} 适用。

\emph{情形 \textsc{T-Rcd}。}对每个字段使用归纳假设。若全部是值，整条
记录就是值；否则，\textsc{E-Rcd} 可以让最先尚未成为值的字段求值一步。

\emph{情形 \textsc{T-Proj}。}若被投影项能求值，使用 \textsc{E-Proj}。
若它已经是值，\cref{lem:15.3.6}说明它是一条记录，而且包含所请求的标签，
因此 \textsc{E-ProjRcd} 适用。

\emph{情形 \textsc{T-Sub}。}直接使用归纳假设。
\end{proof}
\section{Top 与 Bot 类型}
\label{sec:15.4}

最大类型 \(\tapltype{Top}\) 并不是带子类型化的简单类型 lambda 演算所
必需的；删去它不会破坏系统的性质。不过，多数论述仍会保留它。首先，它对应
多数面向对象语言中的 \texttt{Object} 类型。其次，在把子类型化与参数多态
结合的更复杂系统中，\(\tapltype{Top}\) 是很方便的技术工具。例如，在
\SystemF\(_{<:}\)（\chapref{26}和\chapref{28}）中，它使有界量化能够表达
普通的无界量化，从而简化系统。甚至记录也能在 \SystemF\(_{<:}\) 中编码，
而该编码关键依赖 \(\tapltype{Top}\)。最后，它的行为简单，例子里又常有用，
所以没有多少理由把它删掉。

既然已经有了最大类型 \(\tapltype{Top}\)，一个相应的问题是：能否再加入
最小类型 \(\tapltype{Bot}\)，使它成为所有类型的子类型？答案是肯定的，
\cref{fig:15-4}给出了相应规则。

\translatornote{\cref{ex:15.2.4}考察的是加入 \(\tapltype{Bot}\) 之前的类型
语法，结论是其中没有任何现成类型能够成为所有类型的共同子类型。本节随后
扩展类型语法，新增 \(\tapltype{Bot}\)，并用 \textsc{S-Bot} 规定
\(\tapltype{Bot}\subtype T\) 对任意 \(T\) 成立。最小类型来自这次扩展，
因此与该练习的结论并不矛盾。}

首先，\(\tapltype{Bot}\) 是空的：不存在类型为 \(\tapltype{Bot}\) 的闭值。
反设存在这样的值 \(v\)。由 \textsc{S-Bot} 和 \textsc{T-Sub}，可得
\(\vdash v:\tapltype{Top}\to\tapltype{Top}\)；典范形式引理于是要求
\(v\) 是 lambda 抽象。另一方面，同样可得 \(\vdash v:\{\}\)，典范形式
引理又要求 \(v\) 是记录。句法上一个值不可能同时是函数和记录，因此假设导致
矛盾。

空类型并非没有用处。它可以方便地表达某些操作——尤其是抛出异常或调用续延——
不会正常返回。给这类表达式类型 \(\tapltype{Bot}\) 有两个好处：一方面，
类型向程序员表明不应期待结果；另一方面，类型检查器知道该表达式可以安全地
放入需要任意结果类型的上下文。例如，把\chapref{14}的
\(\mathsf{error}\) 赋予 \(\tapltype{Bot}\) 后，下面的项可以赋型：
\[
\lambda x:T.\,
\mathsf{if}\ \langle\text{检查 }x\text{ 是否合理}\rangle\
\mathsf{then}\ \langle\text{计算结果}\rangle\
\mathsf{else}\ \mathsf{error}
\]
正常分支无论具有什么类型，都能由包容规则把 \(\mathsf{error}\) 提升到同一
类型，使两个分支满足 \textsc{T-If}。\footnote{在 ML 一类带多态的语言中，
也可以把 \(\forall X.\,X\) 用作 \(\mathsf{error}\) 等构造的结果类型。
它通过实例化为任意类型达到与 \(\tapltype{Bot}\) 相似的效果；两者虽然原理
不同，都是空类型。}

\newpage
\translatornote{续延（\textit{continuation}）首先是描述普通程序求值过程的
概念。考虑下面的程序：
\[
\begin{array}{l}
x=f();\\
\mathsf{print}(x+1)
\end{array}
\]
执行 \(f\) 时，运行时系统必须记住：\(f\) 返回以后，还要把返回值赋给
\(x\)，计算 \(x+1\)，再打印结果。这段“当前计算得到一个值以后，接下来要
完成的全部工作”就是当前续延；机器通常用调用栈和返回地址保存它。普通的
\(\mathsf{return}\ 5\) 可以理解为把 \(5\) 交给这段续延，让程序恢复调用者
的计算并执行 \(\mathsf{print}(5+1)\)。因此，即使一门语言没有把续延直接
暴露给程序员，它的运行时仍然需要维护类似的信息。

同一概念也可以用带洞的求值上下文表示。例如，程序正在计算
\[
1+(2\times\Box)
\]
时，\(\Box\) 表示当前等待结果的子表达式位置。若这里得到 \(x\)，余下的
计算便是 \(1+(2\times x)\)。所以带洞的上下文
\(1+(2\times\Box)\) 描述了此处的续延；当子表达式求得 \(5\) 时，普通
求值会把 \(5\) 填入洞中，继续得到 \(11\)。

通常，程序只能沿着当前续延继续执行。Scheme 的
\texttt{call-with-current-continuation}（\texttt{call/cc}，也见
\cref{ex:14.3.3}）进一步允许程序把当前续延捕获为一个可调用的值，保存起来
并在以后恢复。设 \(k\) 保存了上面的续延
\(1+(2\times\Box)\)。调用 \(k(5)\) 的含义是：放弃调用时正在使用的续延，
恢复 \(k\) 保存的续延，并让保存位置像是刚刚得到了值 \(5\)。例如，程序后来
正在计算
\[
100+k(5)
\]
时，当前续延是 \(100+\Box\)。调用 \(k(5)\) 会丢弃这个当前续延，恢复
\(1+(2\times\Box)\)，于是程序继续得到 \(11\)，外围的加 \(100\) 不会
执行。相比之下，若 \(h(x)=1+(2\times x)\) 只是普通函数，
\(100+h(5)\) 会正常返回并得到 \(111\)。这个差别说明，捕获的续延代表一条
可以恢复的控制路径；调用它是在替换当前控制路径。

把续延开放给程序后，非局部返回、异常、回溯、协程、生成器和任务调度等控制
结构都可以在它的基础上表达。完整续延的能力很强，许多语言只提供用途更明确
的受限形式，例如异常、生成器和 \texttt{async}/\texttt{await}。

本节只需要其中一个性质：调用这种已捕获的续延不会返回当前调用位置。若续延
等待一个 \(T\) 型值，就可以把它理解成具有类似
\(T\to\tapltype{Bot}\) 的类型；它接收一个值并把控制转移到保存的计算，
当前调用点不会产生正常结果。这正是此处把调用续延与抛出异常并列的原因。}

但 \(\tapltype{Bot}\) 会显著增加类型检查的复杂度。没有它时，若应用
\(t_1\,t_2\) 良类型，就能推断 \(t_1\) 具有箭头类型；有了它，只能推断
\(t_1\) 具有箭头类型或 \(\tapltype{Bot}\)。
\taplsecref{16.4}{sec:16.4}会展开这一点；在有界量化系统中，困难还会被放大，
见\taplsecref{28.8}{sec:28.8}。因此，加入 \(\tapltype{Bot}\) 比加入
\(\tapltype{Top}\) 更重。本书后续章节的主体系统不再把它作为默认组成部分；
上述两节只在局部扩展中考察加入它所带来的问题。

\label{sec:15.5}

把当前演算逐步扩展成完整程序语言时，每加入一种特性，都必须检查它与子类型化
如何相互作用。本节讨论此前见过的若干特性。\footnote{本节讨论的大多数扩展
没有在 \texttt{fullsub} 检查器中实现。}子类型化与参数多态、递归类型和

\subsection*{类型断言与类型转换}

\taplsecref{11.4}{sec:11.4}引入的类型断言 \(t\ \mathsf{as}\ T\) 是一种
经过检查的说明文字，让程序员在程序中记录某个子项应具有的类型。本书例子也
用它控制类型的打印形式，要求类型检查器采用更易读的缩写。

在 Java、C++ 等带子类型化的语言中，这个构造更为重要，常称为
\termfirst{类型转换}{casting}，写作 \((T)t\)。类型转换分成两种性质很不
相同的形式：\termfirst{向上类型转换}{up-cast}和
\termfirst{向下类型转换}{down-cast}。前者直接沿用类型断言，后者需要运行时
类型测试。

向上类型转换把项指定为其自然类型的某个超类型。类型检查器先推导
\(\Gamma\vdash t:S\)，再由 \(S\subtype T\) 和 \textsc{T-Sub} 得到
\(\Gamma\vdash t:T\)，最后应用类型断言规则。完整推导为：
\[
\inferrule*[right=\textsc{T-Ascribe}]
 {\inferrule*[right=\textsc{T-Sub}]
   {\Gamma\vdash t:S\\S\subtype T}
   {\Gamma\vdash t:T}}
 {\Gamma\vdash t\ \mathsf{as}\ T:T}
\]
上图最下面的一步使用的 \textsc{T-Ascribe}，就是\taplsecref{11.4}{sec:11.4}
定义的类型断言规则：
\[
\inferrule*[right=\textsc{T-Ascribe}]
 {\Gamma\vdash t:T}{\Gamma\vdash t\ \mathsf{as}\ T:T}
\]
它可以看作一种抽象手段：把值的某些组成部分隐藏起来，使周围上下文无法使用。
例如，可以通过向上类型转换隐藏记录或对象的一些字段或方法。

向下类型转换允许给项指定静态类型规则无法推导出的类型。为此，把类型断言规则
改为：
\[
\inferrule*[right=\textsc{T-Downcast}]
 {\Gamma\vdash t:S}{\Gamma\vdash t\ \mathsf{as}\ T:T}
\]
这里只检查 \(t\) 本身良类型，不要求 \(S\) 与 \(T\) 有任何静态关系。例如：
\[
f=\lambda x:\tapltype{Top}.\,(x\ \mathsf{as}\
\{a:\tapltype{Nat}\}).a
\]
程序员等于告诉类型检查器：根据类型规则表达不了的外部理由，自己确信 \(f\)
只会接收到含有自然数字段 \(a\) 的记录。

若编译器无条件相信这种断言，语言会失去安全性。实际策略是“信任，但验证”：
编译期接受断言的类型，运行时再检查实际值是否确实属于所声称的类型。因此，
原本直接丢掉断言的规则
\[
\inferrule*[right=\textsc{E-Ascribe}]
 { }{v\ \mathsf{as}\ T\trans v}
\]
改成带运行时类型前提的规则：
\[
\inferrule*[right=\textsc{E-Downcast}]
 {\vdash v:T}{v\ \mathsf{as}\ T\trans v}
\]
把 \(f\) 应用于 \(\{a=5,b=\tapltrue\}\) 时，检查成功；应用于
\(\{b=\tapltrue\}\) 时，规则无法使用，求值卡住。运行时检查恢复了保持性。

\begin{exercise}[\(\star\star\), \(\nrightarrow\)]
\label{ex:15.5.1}
证明加入上述向下类型转换规则后，类型保持性仍然成立。
\end{exercise}
\taplsolutionlink{sol:translator:15.5.1}{15.5.1}

进展性则会失效，因为错误的向下类型转换可以让良类型程序卡住。真实语言通常
把失败的转换变成可捕获的动态异常，或改用动态类型测试：
\[
\inferrule*[right=\textsc{T-TypeTest}]
 {\Gamma\vdash t_1:S\\
  \Gamma,x:T\vdash t_2:U\\
  \Gamma\vdash t_3:U}
 {\Gamma\vdash
  \mathsf{if}\ t_1\ \mathsf{in}\ T\ \mathsf{then}\ x\mapsto t_2\
  \mathsf{else}\ t_3:U}
\]
成功与失败两种求值情形分别是：
\[
\inferrule*[right=\textsc{E-TypeTest1}]
 {\vdash v_1:T}
 {\mathsf{if}\ v_1\ \mathsf{in}\ T\ \mathsf{then}\ x\mapsto t_2\
  \mathsf{else}\ t_3
  \trans [x\mapsto v_1]t_2}
\]
\[
\inferrule*[right=\textsc{E-TypeTest2}]
 {\nvdash v_1:T}
 {\mathsf{if}\ v_1\ \mathsf{in}\ T\ \mathsf{then}\ x\mapsto t_2\
  \mathsf{else}\ t_3
  \trans t_3}
\]

\translatornote{
这里的 \(x\) 是程序员在类型测试表达式中写下的变量名，用来给通过运行时
检查的值命名。可以把
\[
\mathsf{if}\ t_1\ \mathsf{in}\ T\ \mathsf{then}\ x\mapsto t_2\
\mathsf{else}\ t_3
\]
读作：“先求出 \(t_1\) 的值；若该值具有类型 \(T\)，就把它命名为 \(x\)，
然后执行 \(t_2\)；否则执行 \(t_3\)。”箭头 \(\mapsto\) 在这里标记变量
绑定，\(x\) 的作用域仅限于成功分支 \(t_2\)。

静态检查时，只知道 \(t_1\) 具有某个类型 \(S\)。运行时若得到值 \(v_1\)，
并确认 \(v_1:T\)，成功分支便可以在 \(x:T\) 的假设下使用这个值；
\textsc{E-TypeTest1} 通过替换 \([x\mapsto v_1]t_2\) 落实这一绑定。
这个过程不会复制该值，也不会再次求值 \(t_1\)。若检查失败，
\textsc{E-TypeTest2} 直接选择 \(t_3\)，所以失败分支中没有变量 \(x\)。

例如，
\[
\mathsf{if}\ obj\ \mathsf{in}\ \{a:\tapltype{Nat}\}\
\mathsf{then}\ x\mapsto x.a\ \mathsf{else}\ 0
\]
会在 \(obj\) 的实际值含有自然数字段 \(a\) 时，用 \(x\) 表示这个值并读取
\(x.a\)；若检查失败，则返回 \(0\)。
}

Java 一类语言经常使用向下类型转换，其中一个重要用途是模拟一种简陋的
多态机制。旧式 Java 集合类（如 \texttt{Set} 和 \texttt{List}）是单态的：Java
没有为每个类型 \(T\) 提供“元素类型为 \(T\) 的列表”\(\texttt{List}\ T\)，
只有一个 \texttt{List} 类型，其元素统一属于最大类型 \texttt{Object}。
由于每个对象类型都是 \texttt{Object} 的子类型，任意对象都可以先通过包容
规则提升为 \texttt{Object}，再放入列表。可是从列表取出元素时，类型检查器
只知道它具有 \texttt{Object} 类型。这个类型只列出打印等少数所有 Java
对象共有的通用方法，不能保证对象拥有更具体的方法；要实际使用它，程序必须
先把它向下转换成所预期的类型 \(T\)。

Pizza（Odersky 与 Wadler，1997）、Generic Java（GJ；Bracha、Odersky、
Stoutamire 与 Wadler，1998）、PolyJ（Myers、Bank 与 Liskov，1997）以及 NextGen
（Cartwright 与 Steele，1998）的设计者主张，为 Java 类型系统加入真正的
参数多态（见\chapref{23}）。参数多态比上述向下转换惯用法更安全、更高效，
也不需要运行时测试。另一方面，这种扩展会使本已庞大的语言明显复杂化，并与
语言和类型系统的许多其他特性发生作用（例如见 Igarashi、Pierce 与 Wadler，
1999、2001）。因此，也可以把向下转换看作安全性与复杂度之间一种务实的折中。

向下类型转换也是 Java 反射机制的关键。程序员可以要求 Java 运行时系统动态
加载某个字节码文件，并创建其中某个类的实例。静态类型检查器不可能预知此时会
加载怎样的类——字节码甚至可以在需要时从网络取得——所以最多只能把新实例
赋予 \texttt{Object} 类型。要实际使用它，程序仍须把它向下转换为所预期的
类型 \(T\)；若字节码提供的类与 \(T\) 不匹配，还要处理运行时抛出的异常，
成功后才能把对象当作 \(T\) 使用。

从前面的规则看，加入向下转换似乎意味着把整套类型检查机制都搬进运行时系统。
问题还不止于此：值在运行时的表示通常不同于编译器内部的表示，函数尤其会被
编译成字节码或本机机器指令；若直接检查这些运行时表示，似乎还得另写一套用于
动态检查的类型检查器。真实语言通常用\termfirst{类型标签}{type tag}避免这样
做：每个值携带一个机器字大小的标签，保存编译期类型在运行时留下的必要信息。
这种标签在某些方面类似于 ML 数据类型的构造子和\taplsecref{11.10}{sec:11.10}
的变体标签，已经足以完成动态子类型测试。\chapref{19}将详细说明这种机制的
一种具体形式。

\subsection*{变体}

变体的子类型规则与记录几乎相同，差别在于宽度规则的方向：从子类型移向超类型
时，可以增加变体标签。带标签的值 \(\langle l=t\rangle\) 属于列出标签 \(l\)
的变体类型；类型列出的可能标签越多，对值提供的信息越少。单标签类型
\(\langle l_1:T_1\rangle\) 精确说明其中的值都带标签 \(l_1\)，双标签类型
\(\langle l_1:T_1,l_2:T_2\rangle\) 只能说明值带 \(l_1\) 或 \(l_2\)，其余
情形依此类推。反过来，使用变体值时总要写 \(\mathsf{case}\)，并为类型列出的
每个标签提供分支；类型中增加标签，只会迫使 \(\mathsf{case}\) 多写一些可能
永远用不到的分支。

\subsection*{列表}

前面已经见过多种协变关系：记录字段和变体分支所携带的类型都是协变的，
函数的返回类型也是协变的；函数的参数类型则是逆变的。列表的元素类型同样
是协变的：若
\(S_1\subtype T_1\)，则元素类型为 \(S_1\) 的列表可以安全地看作元素类型
为 \(T_1\) 的列表。
\[
\inferrule*[right=\textsc{S-List}]
 {S_1\subtype T_1}
 {\tapltype{List}\ S_1\subtype\tapltype{List}\ T_1}
\]

\subsection*{引用}

并非所有类型构造子都协变或逆变。为了保持类型安全，\(\tapltype{Ref}\)
必须是不变的：
\[
\inferrule*[right=\textsc{S-Ref}]
 {S_1\subtype T_1\\T_1\subtype S_1}
 {\tapltype{Ref}\ S_1\subtype\tapltype{Ref}\ T_1}
\]
只有当引用中存放的类型 \(S_1\) 与 \(T_1\) 互为子类型时，才能建立
\(\tapltype{Ref}\ S_1\) 与 \(\tapltype{Ref}\ T_1\) 之间的子类型关系。
这允许记录字段的排列顺序不同，却不允许改变引用实际能够保存的值。

限制来自引用的读写两种用途。读取 \(\tapltype{Ref}\ T_1\) 时，上下文期望
得到 \(T_1\)；若引用实际存放 \(S_1\)，必须有 \(S_1\subtype T_1\)。写入
时，上下文提供 \(T_1\)；若引用实际类型是 \(\tapltype{Ref}\ S_1\)，以后
别处可能把新值当作 \(S_1\) 读出，所以还必须有 \(T_1\subtype S_1\)。

\begin{exercise}[\(\star\), \(\nrightarrow\)]
\label{ex:15.5.2}
\begin{enumerate}
\item 若删去 \textsc{S-Ref} 的第一个前提，写一个会在运行时发生类型错误
  （即求值卡住）的短程序。
\item 若删去第二个前提，再写一个这样的程序。
\end{enumerate}
\end{exercise}

\subsection*{数组}

数组同样既能读取又能写入，所以也应采用不变规则。Java 却允许数组协变：若
\(S_1\subtype T_1\)，则 \(S_1[]\subtype T_1[]\)。这项设计最初用于弥补
若干基本数组操作缺少参数多态，如今普遍被视为缺陷。为了补偿不安全的规则，
运行时必须检查每次数组写入，确认待写值属于数组实际元素类型的子类型，影响了
数组程序的性能。
\[
\inferrule*[right=\textsc{S-Array}]
 {S_1\subtype T_1\\T_1\subtype S_1}
 {\tapltype{Array}\ S_1\subtype\tapltype{Array}\ T_1}
\qquad
\inferrule*[right=\textsc{S-ArrayJava}]
 {S_1\subtype T_1}
 {\tapltype{Array}\ S_1\subtype\tapltype{Array}\ T_1}
\]

\begin{exercise}[\(\star\star\star\), \(\nrightarrow\)]
\label{ex:15.5.3}
写一个涉及数组的短 Java 程序：它能通过类型检查，却会在运行时抛出
\texttt{ArrayStoreException}。
\end{exercise}

\subsection*{再次考察引用}

Reynolds 在 Forsythe（1988）中率先提出更精细的引用分析：引入
\(\tapltype{Source}\) 和 \(\tapltype{Sink}\) 两个构造子，分别表示对
引用单元的读取权限和写入权限。具体而言，\(\tapltype{Source}\ T\) 只允许
从单元读取 \(T\) 型值，\(\tapltype{Sink}\ T\) 只允许向单元写入 \(T\)
型值；原有的 \(\tapltype{Ref}\ T\) 则同时保留这两种权限，既可读取，也可
写入。相应类型规则只要求所需能力：
\[
\inferrule*[right=\textsc{T-Deref}]
 {\Gamma\vdash t_1:\tapltype{Source}\ T_{11}}
 {\Gamma\vdash {!t_1}:T_{11}}
\qquad
\inferrule*[right=\textsc{T-Assign}]
 {\Gamma\vdash t_1:\tapltype{Sink}\ T_{11}\\
  \Gamma\vdash t_2:T_{11}}
 {\Gamma\vdash t_1:=t_2:\tapltype{Unit}}
\]
只读能力协变，只写能力逆变：
\[
\inferrule*[right=\textsc{S-Source}]
 {S_1\subtype T_1}
 {\tapltype{Source}\ S_1\subtype\tapltype{Source}\ T_1}
\qquad
\inferrule*[right=\textsc{S-Sink}]
 {T_1\subtype S_1}
 {\tapltype{Sink}\ S_1\subtype\tapltype{Sink}\ T_1}
\]

\translatornote{
可以把 \(\tapltype{Source}\ T\) 看作一个返回 \(T\) 型值的函数
\(\tapltype{Unit}\to T\)，把 \(\tapltype{Sink}\ T\) 看作一个接收
\(T\) 型值的函数 \(T\to\tapltype{Unit}\)。因此，前者与函数的返回类型
一样协变，后者与函数的参数类型一样逆变。

例如，若 \(\tapltype{Dog}\subtype\tapltype{Animal}\)，那么
\[
\tapltype{Sink}\ \tapltype{Animal}
\subtype
\tapltype{Sink}\ \tapltype{Dog}
\]
一个能够接收任意动物的写入口，可以安全地交给只会写入狗的程序使用。反方向
并不安全：若把只能接收狗的入口当作能够接收任意动物的入口，使用者便可能向
其中写入一只猫。\(\tapltype{Sink}\) 中的类型参数因而反转了原来的子类型
方向。
}

引用则可以降为其中任一种能力：
\[
\inferrule*[right=\textsc{S-RefSource}]
 { }{\tapltype{Ref}\ T_1\subtype\tapltype{Source}\ T_1}
\qquad
\inferrule*[right=\textsc{S-RefSink}]
 { }{\tapltype{Ref}\ T_1\subtype\tapltype{Sink}\ T_1}
\]

\subsection*{信道}

Pict 等并发语言中的信道类型也区分读写权限，并采用与
\(\tapltype{Source}\)、\(\tapltype{Sink}\) 相同的子类型规则。从类型角度
看，通信信道与引用单元类似：程序既可以向信道写入（发送）值，也可以从信道
读取（接收）值。静态分析通常很难确定某次读取会接收到哪次写入的值，因此，
保证安全的一种简单办法是要求同一信道上传递的所有值具有相同的类型。

两种信道权限的变型方向也与引用相同。若某个信道允许写入 \(S\) 型值，而
\(T\subtype S\)，那么它可以安全地交给只会写入 \(T\) 型值的程序使用，
因此输出信道类型构造子是逆变的。若从某个信道读出的值保证具有类型 \(S\)，
而 \(S\subtype T\)，那么这些值也可以作为 \(T\) 型值读取，因此输入信道
类型构造子是协变的。
关于这种信道类型的进一步讨论，见 Pierce 与 Turner（2000）以及 Pierce 与
Sangiorgi（1993）。

\subsection*{基本类型}

在基本类型较多的语言中，常会在它们之间加入原始子类型关系。例如，若语言用
数字 \(1\) 和 \(0\) 表示布尔值，可以公开实现细节并加入公理
\(\tapltype{Bool}\subtype\tapltype{Nat}\)。此后可写紧凑的 \(5*b\)，
而不必写 \(\mathsf{if}\ b\ \mathsf{then}\ 5\ \mathsf{else}\ 0\)。

\section{子类型化的强制转换语义}
\label{sec:15.6}

到目前为止，子类型化在语义上没有改变程序的求值方式，只让项的赋型更灵活。
这种解释简单自然，但可能给数值计算和记录字段访问带来高性能实现无法接受的
开销。本节概述另一种\termfirst{强制转换语义}{coercion semantics}，并讨论
它引出的新问题；读者可以跳过本节。

\subsection*{子集语义的性能问题}

设加入 \(\tapltype{Int}\subtype\tapltype{Float}\)，允许把整数直接用于浮点
运算。例如，原本需要写成 \(4.5+\mathit{intToFloat}(6)\) 的表达式，现在可以
简写为 \(4.5+6\)。子集语义要求
整数值集合确实是浮点值集合的子集。但真实机器通常用补码表示整数，用尾数、
指数和符号位表示浮点数，还为 \(\mathsf{NaN}\)（非数）等特殊值保留编码；
两者的具体表示完全不同。

一种兼容子集语义的办法，是让所有数都采用带标签（或装箱）的共同表示：机器
整数附带整数标签，机器浮点数附带另一种标签。标签既可单独占用一个头部机器字，
也可放在保存实际整数那个机器字的高位。此时 \(\tapltype{Float}\) 描述所有
带标签的数，包括浮点数和整数；\(\tapltype{Int}\) 只描述带整数标签的数。

这种方案并不荒唐，许多现代语言实现确实采用类似策略，标签位或标签字也能为
垃圾回收提供信息。代价是每个基本数值操作都要先检查实参标签，用若干指令拆箱
出机器数，执行真正的运算，再用若干指令把结果重新装箱。编译器优化可以消除
部分开销，但即使采用目前最好的技术，在图形和科学计算等数值密集程序中仍会
显著降低性能。

记录排列规则会造成另一种问题。简单的字段投影规则
\[
\inferrule*[right=\textsc{E-ProjRcd}]
 { }{\{l_i=v_i\}^{i\in1..n}.l_j\trans v_j}
\]
可以读作“在记录的标签中搜索 \(l_j\)，并返回与它关联的值 \(v_j\)”。真实
实现当然不愿在运行时线性扫描整条记录。若语言没有子类型化，或者有子类型化
却没有排列规则，而标签 \(l_j\) 在记录类型中列为第三个字段，编译器就能静态
确定：该类型的每个运行时值也把 \(l_j\) 放在第三个字段。因此运行时完全不必
查看标签；甚至可以删掉标签，把记录编译成元组。访问 \(l_j\) 时，只需通过
指向记录起始处的寄存器间接读取，再加上固定的三个机器字偏移。

排列规则破坏了这种技术。即使某个记录值属于一个把 \(l_j\) 列在第三位的类型，
我们也无法据此判断它在实际记录中存放在哪里。优化和运行时技巧可以缓解问题，
但一般而言，字段投影仍可能需要某种运行时搜索。\footnote{类似情况也出现在允许
对象子类型排列的语言中访问对象字段和方法时。因此，Java 类之间的子类型化
只允许在末尾添加字段。接口之间、类与接口之间则允许排列——否则接口几乎
失去用途——Java 手册也明确提醒，接口方法查找通常比类方法查找慢。}

\subsection*{强制转换语义}

另一种语义把子类型化“编译掉”，以运行时强制转换取而代之。把
\(\tapltype{Int}\) 提升到 \(\tapltype{Float}\) 时，运行时真正把机器整数
改为机器浮点表示；使用记录排列规则时，则生成实际重排字段的代码。这样，
基本数值操作和字段访问无需承担拆箱或搜索开销。

形式上，强制转换语义把带子类型化的源语言项翻译到不带子类型化的低层语言。
这里以带记录的 \(\lambda_{<:}\) 为源语言，以带记录和
\(\tapltype{Unit}\) 的纯简单类型 lambda 演算为目标语言；
\(\tapltype{Unit}\) 用来解释 \(\tapltype{Top}\)。编译包含类型、子类型
推导和类型推导三种翻译，都写作 \(\llbracket-\rrbracket\)，上下文会说明正在
翻译哪一种对象。

类型翻译为：
\[
\begin{aligned}
\llbracket\tapltype{Top}\rrbracket
  &=\tapltype{Unit},\\
\llbracket T_1\to T_2\rrbracket
  &=\llbracket T_1\rrbracket\to\llbracket T_2\rrbracket,\\
\llbracket\{l_i:T_i\}^{i\in1..n}\rrbracket
  &=\{l_i:\llbracket T_i\rrbracket\}^{i\in1..n}
\end{aligned}
\]
例如，
\(\llbracket\tapltype{Top}\to
\{a:\tapltype{Top},b:\tapltype{Top}\}\rrbracket=
\tapltype{Unit}\to\{a:\tapltype{Unit},b:\tapltype{Unit}\}\)。

翻译项时必须知道类型推导在哪里使用了包容规则，因为这些位置要插入运行时
强制转换。同样，要生成从 \(S\) 到 \(T\) 的强制转换函数，仅知道
\(S\subtype T\) 还不够，还必须知道这个判断怎样推导出来。因此，翻译以推导
本身为输入。写 \(\mathcal C::S\subtype T\)，表示 \(\mathcal C\) 是结论
为该判断的子类型推导树；写 \(\mathcal D::\Gamma\vdash t:T\)，表示
\(\mathcal D\) 是相应类型推导树。

设 \(\mathcal C\) 是一棵证明 \(S\subtype T\) 的子类型推导树。翻译时，
我们把这棵推导树编译成目标语言中的一个显式转换函数
\(\llbracket\mathcal C\rrbracket\)。该函数接收一个
\(\llbracket S\rrbracket\) 型值，返回一个 \(\llbracket T\rrbracket\) 型值。
具体生成什么函数，取决于推导树 \(\mathcal C\) 最后一步所用的子类型规则：
\[
\begin{array}{rcl}
\llbracket\textsc{S-Refl}_T\rrbracket
 &=&\lambda x:\llbracket T\rrbracket.\,x\\[2pt]
\llbracket\textsc{S-Top}_S\rrbracket
 &=&\lambda x:\llbracket S\rrbracket.\,\mathsf{unit}\\[2pt]
\llbracket\textsc{S-Trans}(\mathcal C_1,\mathcal C_2)\rrbracket
 &=&\lambda x:\llbracket S\rrbracket.\,
     \llbracket\mathcal C_2\rrbracket
       (\llbracket\mathcal C_1\rrbracket x)\\[2pt]
\llbracket\textsc{S-Arrow}(\mathcal C_1,\mathcal C_2)\rrbracket
 &=&\lambda f:\llbracket S_1\to S_2\rrbracket.\,
     \lambda x:\llbracket T_1\rrbracket.\,
     \llbracket\mathcal C_2\rrbracket
       (f(\llbracket\mathcal C_1\rrbracket x))\\[2pt]
\llbracket\textsc{S-RcdWidth}\rrbracket
 &=&\lambda r:\{l_i:\llbracket T_i\rrbracket\}^{i\in1..n+m}.\,
     \{l_i=r.l_i\}^{i\in1..n}\\[2pt]
\llbracket\textsc{S-RcdDepth}(\mathcal C_i)\rrbracket
 &=&\lambda r:\{l_i:\llbracket S_i\rrbracket\}^{i\in1..n}.\,
     \{l_i=\llbracket\mathcal C_i\rrbracket(r.l_i)\}^{i\in1..n}\\[2pt]
\llbracket\textsc{S-RcdPerm}\rrbracket
 &=&\lambda r:\{k_j:\llbracket S_j\rrbracket\}^{j\in1..n}.\,
     \{l_i=r.l_i\}^{i\in1..n}
\end{array}
\]

\begin{lemma}
\label{lem:15.6.1}
若 \(\mathcal C\) 是 \(S\subtype T\) 的一棵合法推导树，那么由它生成的
强制转换 \(\llbracket\mathcal C\rrbracket\) 也是目标语言中的良类型函数：
它接收一个 \(\llbracket S\rrbracket\) 型的值，返回一个
\(\llbracket T\rrbracket\) 型的值。即
\[
\vdash\llbracket\mathcal C\rrbracket:
\llbracket S\rrbracket\to\llbracket T\rrbracket
\]
\end{lemma}
\begin{proof}
对 \(\mathcal C\) 作直接归纳。
\end{proof}

接下来定义如何根据类型推导树生成目标语言程序。若
\(\mathcal D::\Gamma\vdash t:T\)，则 \(\llbracket\mathcal D\rrbracket\)
表示根据整棵推导树 \(\mathcal D\) 生成的目标语言项。普通类型规则只需递归
翻译程序的各个子项：变量仍是自身，抽象、应用、记录和投影仍保留原有结构。
关键是 \textsc{T-Sub}：源程序中没有写出的子类型转换会记录在这个推导节点中，
因此翻译到不带子类型化的目标语言时，必须在这里插入相应的显式强制转换：
\[
\begin{array}{rcl}
\llbracket\textsc{T-Var}_x\rrbracket&=&x\\
\llbracket\textsc{T-Abs}(\mathcal D_2)\rrbracket
 &=&\lambda x:\llbracket T_1\rrbracket.\,\llbracket\mathcal D_2\rrbracket\\
\llbracket\textsc{T-App}(\mathcal D_1,\mathcal D_2)\rrbracket
 &=&\llbracket\mathcal D_1\rrbracket\,\llbracket\mathcal D_2\rrbracket\\
\llbracket\textsc{T-Rcd}(\mathcal D_i)\rrbracket
 &=&\{l_i=\llbracket\mathcal D_i\rrbracket\}^{i\in1..n}\\
\llbracket\textsc{T-Proj}(\mathcal D_1)\rrbracket
 &=&\llbracket\mathcal D_1\rrbracket.l_j\\
\llbracket\textsc{T-Sub}(\mathcal D,\mathcal C)\rrbracket
 &=&\llbracket\mathcal C\rrbracket\,\llbracket\mathcal D\rrbracket
\end{array}
\]
这项翻译常称为\termfirst{Penn 翻译}{Penn translation}，名称来自最早研究它的
宾夕法尼亚大学团队（Breazu-Tannen、Coquand、Gunter 与 Scedrov，1991）。

\begin{theorem}
\label{thm:15.6.2}
若推导树 \(\mathcal D\) 证明源语言中的项 \(t\) 在上下文 \(\Gamma\) 下
具有类型 \(T\)，那么根据 \(\mathcal D\) 生成的目标语言项
\(\llbracket\mathcal D\rrbracket\)，在翻译后的上下文
\(\llbracket\Gamma\rrbracket\) 下也具有翻译后的类型
\(\llbracket T\rrbracket\)。即
\[
\mathcal D::\Gamma\vdash t:T
\quad\Longrightarrow\quad
\llbracket\Gamma\rrbracket\vdash
\llbracket\mathcal D\rrbracket:\llbracket T\rrbracket
\]
换言之，这项翻译会保持程序的类型正确性。其中，上下文中的绑定分别翻译：
\(\llbracket\varnothing\rrbracket=\varnothing\)，且
\(\llbracket\Gamma,x:T\rrbracket=
\llbracket\Gamma\rrbracket,x:\llbracket T\rrbracket\)。
\end{theorem}
\begin{proof}
对 \(\mathcal D\) 作直接归纳；\textsc{T-Sub} 情形使用
\cref{lem:15.6.1}。
\end{proof}

有了这些翻译，可以不再给高级语言直接定义求值规则。求值一个项时，先用高级
语言的类型规则和子类型规则检查它，再把类型推导翻译到低层目标语言，最后使用目标
语言的求值关系。某些高性能子类型语言实现确实采用这种策略（League、Shao 与
Trifonov，1999；League、Trifonov 与 Shao，2001）。

\begin{exercise}[\(\star\star\star\), \(\nrightarrow\)]
\label{ex:15.6.3}
修改上述翻译，以带元组而非记录的简单类型 lambda 演算作为目标语言，并检查
\cref{thm:15.6.2}仍然成立。
\end{exercise}

\subsection*{一致性}

强制转换语义还要避免一个陷阱。设语言含有 \(\tapltype{Int}\)、
\(\tapltype{Bool}\)、\(\tapltype{Float}\) 和 \(\tapltype{String}\)，并
提供如下基本转换：
\[
\begin{array}{rcl}
\llbracket\tapltype{Bool}\subtype\tapltype{Int}\rrbracket
 &=&\lambda b:\tapltype{Bool}.\,
     \mathsf{if}\ b\ \mathsf{then}\ 1\ \mathsf{else}\ 0\\
\llbracket\tapltype{Int}\subtype\tapltype{String}\rrbracket
 &=&\mathit{intToString}\\
\llbracket\tapltype{Bool}\subtype\tapltype{Float}\rrbracket
 &=&\lambda b:\tapltype{Bool}.\,
     \mathsf{if}\ b\ \mathsf{then}\ 1.0\ \mathsf{else}\ 0.0\\
\llbracket\tapltype{Float}\subtype\tapltype{String}\rrbracket
 &=&\mathit{floatToString}
\end{array}
\]
设 \(\mathit{intToString}(1)=\texttt{"1"}\)，而
\(\mathit{floatToString}(1.0)=\texttt{"1.000"}\)。项
\((\lambda x:\tapltype{String}.\,x)\ \tapltrue\) 可以沿两条路径赋型：把
\(\tapltype{Bool}\) 先提升到 \(\tapltype{Int}\) 再到
\(\tapltype{String}\)，或先提升到 \(\tapltype{Float}\) 再到
\(\tapltype{String}\)。两棵类型推导树翻译出的程序分别得到
\texttt{"1"} 和 \texttt{"1.000"}。程序员只写项，不写推导；若编译器内部
选择的推导能改变程序行为，语言的行为便无法由程序员预测。

为避免这一问题，翻译必须满足\termfirst{一致性}{coherence}。

\begin{definition}
\label{def:15.6.4}
从一种语言的类型推导到另一种语言项的翻译
\(\llbracket-\rrbracket\) 称为一致的，如果对任意两棵具有同一结论
\(\Gamma\vdash t:T\) 的推导 \(\mathcal D_1\) 和 \(\mathcal D_2\)，
目标语言项 \(\llbracket\mathcal D_1\rrbracket\) 与
\(\llbracket\mathcal D_2\rrbracket\) 在行为上等价。
\end{definition}

没有基本类型时，上面的翻译是一致的。加入前述基本类型公理后，只需规定
\[
\mathit{floatToString}(0.0)=\texttt{"0"},
\qquad
\mathit{floatToString}(1.0)=\texttt{"1"}
\]
即可恢复这个例子中的一致性。对复杂语言证明一致性可能相当困难；相关研究见
Reynolds（1980、1991）、Breazu-Tannen 等（1991）以及 Curien 与
Ghelli（1992）。

\section{交类型与并类型}
\label{sec:15.7}

在类型语言中加入交运算，可以显著增强子类型关系。
交类型由 Coppo、Dezani、Sall\'e 和 Pottinger 提出（Coppo 与
Dezani-Ciancaglini，1978；Coppo、Dezani-Ciancaglini 与 Sall\'e，1979；
Pottinger，1980）。Reynolds（1988、1998b）、Hindley（1992）和
Pierce（1991b）给出了较易入门的介绍。\(T_1\wedge T_2\) 的居留元同时属于 \(T_1\) 与 \(T_2\)，
所以它是序理论中两者的交，即最大下界。这由三条规则表达：
\[
T_1\wedge T_2\subtype T_1
\quad\textsc{(S-Inter1)}
\qquad
T_1\wedge T_2\subtype T_2
\quad\textsc{(S-Inter2)}
\]
\[
\inferrule*[right=\textsc{S-Inter3}]
 {S\subtype T_1\\S\subtype T_2}
 {S\subtype T_1\wedge T_2}
\]
交类型与箭头类型之间还满足下面的子类型关系：
\[
(S\to T_1)\wedge(S\to T_2)\subtype S\to(T_1\wedge T_2)
\qquad\textsc{(S-Inter4)}
\]
如果一项同时具有函数类型 \(S\to T_1\) 和 \(S\to T_2\)，那么给它一个
\(S\) 型实参后，结果同时具有 \(T_1\) 和 \(T_2\)。

下面这个事实说明了交类型的能力：在按名调用的、带子类型化和交类型的简单类型
lambda 演算中，可以获得类型的无类型 lambda 项恰好就是可规范化项——也就
是说，一个无类型 lambda 项能够获得某种类型，当且仅当其求值会终止。由此
立即可知，带交类型演算的类型重构问题（\chapref{22}）不可判定。

\translatornote{这里的关键是，交类型把类型重构与终止性连成了同一个判定
问题。类型重构接收一个没有类型标注的 lambda 项，并尝试为它找到一种类型；
若不存在这样的类型，也应给出否定答案。普通简单类型系统只能保证“能够找到
类型的项一定会终止”，反方向并不成立。例如，\(\lambda x.\,x\,x\) 已经是
正规形式，因为 \(x\,x\) 左侧的 \(x\) 只是变量，不会触发 \(\beta\) 规约；
但同一个 \(x\) 在这里既要作为函数又要作为参数，普通简单类型系统无法为它
找到一种同时满足两种用法的类型。交类型允许令
\(x:(A\to B)\wedge A\)，于是整个抽象可获得类型
\(((A\to B)\wedge A)\to B\)。更一般地，书中引用的结果表明：
\[
\text{一个无类型 lambda 项能够获得交类型}
\quad\Longleftrightarrow\quad
\text{它的求值会终止}
\]
因此，若存在一个总能完成的交类型重构算法，只需观察它能否找到类型，就能
判断任意无类型 lambda 项的求值是否会终止。终止性不可判定，所以一般交类型
的类型重构也不可判定。一般交类型强大的描述能力与这里的不可判定性正是同一
件事的两个方面。}

在实践中，交类型支持有限重载。例如，可以把
\[
(\tapltype{Nat}\to\tapltype{Nat}\to\tapltype{Nat})
\wedge
(\tapltype{Float}\to\tapltype{Float}\to\tapltype{Float})
\]
赋给既能做自然数加法又能做浮点加法的运算符；运行时可按参数标签选择指令。
交类型的能力也带来棘手的语言设计问题。迄今只有一种完整规模语言全面采用一般
交类型，即 Forsythe（Reynolds，1988）；受限的\termfirst{精化类型}{refinement
type}可能更易管理（Freeman 与 Pfenning，1991；Pfenning，1993b；
Davies，1997）。

\translatornote{“精化类型”（refinement type，也常译作“细化类型”）在已有
类型之上描述更精确的静态性质。例如，可以把一般列表类型进一步区分为非空列表
或单元素列表，使类型检查器能够排除只会在空列表上发生的错误。不同系统表达这些
性质的方式并不相同；现代系统常见 \(\{x:T\mid P(x)\}\) 这样的写法，表示
满足条件 \(P\) 的 \(T\) 型值。本段所引 Freeman--Pfenning 系统只为原本已经
通过 ML 类型检查的程序增加由程序员声明的精化信息，从而保留类型推断的可判定性；
这正是它比一般交类型更易于实现和使用之处。}

对偶的\termfirst{并类型}{union type} \(T_1\vee T_2\) 也很有用。它与和类型
和带标签变体不同：\(T_1\vee T_2\) 只是 \(T_1\) 与 \(T_2\) 的普通值集合
之并，不增加标明来源的标签，所以 \(\tapltype{Nat}\vee\tapltype{Nat}\)
只是 \(\tapltype{Nat}\) 的另一个名字。无标签并类型长期用于程序分析
（Palsberg 与 Pavlopoulou，1998），却只见于少数程序语言，其中包括
Algol 68（参见 van Wijngaarden 等，1975）。近来，它还被用于 XML 等
半结构化数据库格式的类型系统（Buneman 与 Pierce，1998；Hosoya、Vouillon
与 Pierce，2001）。

不交并类型（即和类型与带标签变体）同这里的无标签并类型相比，形式上的主要
区别是：后者没有 \(\mathsf{case}\) 构造。若只
知道 \(v:T_1\vee T_2\)，唯一安全的操作是对 \(T_1\) 和 \(T_2\) 都适用的
操作。例如，若二者都是记录，只能投影共有字段。C 的无标签 union 允许执行只
适用于其中一种类型的操作，即使其中实际存放的值来自另一种类型；这种做法忽略
了上述限制，因而会破坏类型安全。

\section{注记}
\label{sec:15.8}

程序语言中的子类型化思想可追溯到 20 世纪 60 年代的 Simula 及其相关语言。
相关介绍见 Birtwistle、Dahl、Myhrhaug 与 Nygaard（1979）。
最早的形式化处理来自 Reynolds（1980）和 Cardelli（1984）。

记录的类型规则，尤其是子类型规则，比此前多数规则都重：它们或含有数目可变
的前提——每个字段一个——或要额外处理字段下标的排列。其他写法也有类似复杂度，
或者依靠省略号等非正式约定回避它。Cardelli 与 Mitchell（1991）为此发展了
“记录上的运算”演算，把构造多字段记录的宏操作拆成空记录值与逐次加入一个
字段的基本操作；在同一框架中还可加入原地字段更新和记录拼接（Harper 与
Pierce，1991）。带参数多态时，这些运算的
类型规则会相当微妙，多数语言设计者因此仍采用普通记录。不过，这套系统在概念
上仍是重要里程碑。Wand（1987、1988、1989b）、R\'emy（1989、1990、1992）
等人发展的另一条路线以行变量多态为基础，后来成为 OCaml 面向对象特性的
基础（R\'emy 与 Vouillon，1998；Vouillon，2000）。

\bilingualepigraph[0.78\textwidth]
  {类型理论要解决的根本问题，是保证程序有意义。类型理论带来的根本问题，
   是有意义的程序未必能被赋予类型。对更丰富类型系统的追求，正源于这层张力。}
  {The fundamental problem addressed by a type theory is to insure that programs have meaning.\\
   The fundamental problem caused by a type theory is that meaningful programs may not have meanings ascribed to them.\\
   The quest for richer type systems results from this tension.}
  {——Mark Manasse}
